Chunkless RAG

Chunkless RAG is a document-retrieval approach where you avoid splitting documents into fixed-size chunks and instead let an AI system retrieve and navigate meaningful document structures—such as sections, pages, tables, paragraphs, figures, and relationships between them.

Traditional RAG

A typical RAG pipeline looks like:


PDF
 ↓
Extract text
 ↓
Split into chunks
 ↓
Create embeddings
 ↓
Vector database
 ↓
Similarity search
 ↓
LLM

For example, a 100-page PDF might become:


Document
 ├── Chunk 1
 ├── Chunk 2
 ├── Chunk 3
 ├── ...
 └── Chunk 500

The problem is that chunks don't necessarily correspond to meaning.

A table can be split in half. A heading can be separated from its paragraph. A question may require information from several sections.

Chunkless RAG

Instead of treating the document as a bag of chunks, you preserve its document structure:


PDF
 ↓
Docling
 ↓
Structured Document
 ↓
 ├── Title
 ├── Section
 │    ├── Paragraph
 │    ├── Table
 │    └── Figure
 ├── Section
 │    ├── Paragraph
 │    └── Table
 └── References
 ↓
AI Agent
 ↓
Navigate relevant parts
 ↓
Answer

The key idea is:

Don't just retrieve pieces of text. Retrieve and navigate the document.

Where Docling fits

Docling is useful because it converts complex documents into structured representations while preserving things such as:

  • headings
  • paragraphs
  • tables
  • lists
  • figures
  • page boundaries
  • reading order
  • document hierarchy

So instead of:


"Revenue increased 12%..."
"Table 4..."
"Operating expenses..."

you can maintain something conceptually closer to:


{
    "section": "Financial Results",
    "children": [
        {
        "type": "paragraph",
        "text": "Revenue increased 12%..."
        },
        {
        "type": "table",
        "caption": "Table 4 - Revenue by Region"
        }
    ]
}

That structure becomes extremely useful for an AI agent.

How the Agent Navigates

Imagine you ask:

"Why did operating expenses increase in 2025?"

A traditional RAG system might search embeddings and retrieve:


Chunk 182
Chunk 247
Chunk 391

A document-aware agent can reason more like:


User question
      ↓
Find "operating expenses"
      ↓
Locate Financial Results
      ↓
Inspect subsection
      ↓
Find related table
      ↓
Inspect footnote
      ↓
Navigate to explanation
      ↓
Answer

In other words, the agent can perform something resembling:


search()
   ↓
open_section()
   ↓
inspect_table()
   ↓
follow_reference()
   ↓
read_context()
   ↓
answer()

This is closer to browsing a document than searching a vector database.

Chunkless ≠ No Retrieval

This is an important distinction.

"Chunkless RAG" doesn't necessarily mean:

Never split anything.

It usually means that fixed arbitrary chunks aren't the primary representation of knowledge.

You can still use:

  • paragraph-level retrieval
  • section-level retrieval
  • semantic search
  • vector embeddings
  • BM25
  • metadata filtering
  • graph relationships
  • page references

For example:


Document
   │
   ├── Section
   │     ├── Paragraph
   │     ├── Paragraph
   │     └── Table
   │
   ├── Section
   │     └── Paragraph
   │
   └── References

Each node can potentially be searchable.

Why This Is Interesting for Your RAG Project

For a research/publication repository, this approach can be especially useful.

Instead of storing:


publication_123_chunk_001
publication_123_chunk_002
publication_123_chunk_003

you could model:


Publication
│
├── Metadata
│
├── Abstract
│
├── Introduction
│
├── Methodology
│   ├── Dataset
│   ├── Experimental Setup
│   └── Evaluation
│
├── Results
│   ├── Table 1
│   ├── Table 2
│   └── Figure 3
│
├── Discussion
│
└── References

Then your AI agent can answer questions by navigating this structure.

For example:

"Compare the methodology used in papers A and B."

The agent could do:


Paper A
 └── Methodology
      └── Experimental Setup

Paper B
 └── Methodology
      └── Experimental Setup

              ↓

          Compare

That's much more powerful than simply retrieving the top 10 similar chunks.

A Practical Architecture

I'd design a modern system like this:


                ┌───────────────┐
                │ PDF / DOCX    │
                └───────┬───────┘
                        ↓
                 ┌─────────────┐
                 │   Docling   │
                 └──────┬──────┘
                        ↓
             Structured Document
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
      Sections       Tables        Figures
          │             │             │
          └─────────────┼─────────────┘
                        ↓
                Document Store
                        │
          ┌─────────────┴─────────────┐
          ↓                           ↓
    Vector Search               Structure Search
          │                           │
          └─────────────┬─────────────┘
                        ↓
                   AI Agent
                        ↓
              Navigate / Retrieve
                        ↓
                     LLM
                        ↓
                    Answer

The best implementation is often hybrid, rather than purely chunkless.

Hybrid RAG

Use vectors for:

"Find concepts related to transformer architectures."

Use structure for:

"What does Section 4.2 say?"

Use tables for:

"What was the accuracy for Dataset B?"

Use references for:

"Which paper does this claim cite?"

The agent decides which mechanism to use.

The big conceptual difference

Traditional RAG


Question
 ↓
Similarity search
 ↓
Top chunks
 ↓
LLM

Agentic / chunkless RAG


Question
 ↓
Understand intent
 ↓
Search document
 ↓
Locate relevant structure
 ↓
Navigate
 ↓
Inspect surrounding context
 ↓
Retrieve supporting evidence
 ↓
Reason
 ↓
Answer

That's why Docling + an AI agent is interesting: Docling gives you a much richer representation of the document, while the agent can use that representation as a navigation space rather than treating the PDF as a pile of independent text chunks.

If you're building your Next.js + RAG research repository, this architecture could be a very good fit: Docling → structured document tree → hybrid retrieval → agentic navigation → citations back to page/section/table.
