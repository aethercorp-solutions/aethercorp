When you tap an iOS app icon

When you tap an iOS app icon, a long chain of system-level processes happens before your UI appears on screen. The process involves the operating system, security checks, memory management, the app lifecycle, rendering systems, and event handling.

Here’s a detailed breakdown of how an iOS application runs inside the iOS system.

1. User Taps the App Icon

When the user taps the app icon on the Home Screen:

  1. The SpringBoard process receives the tap.
  2. SpringBoard is the iOS system app responsible for:
    • Home Screen
    • App launching
    • App switching
    • Notifications
    • Basic window management

The icon contains metadata pointing to the app bundle installed on the device.

2. iOS Locates the App Bundle

An iOS app is packaged as an .app bundle.

Inside the bundle are:

  • Executable binary
  • Assets
  • Storyboards
  • Frameworks
  • Info.plist
  • Resources

Example structure:


MyApp.app/
 ├── MyApp              ← executable binary
 ├── Info.plist
 ├── Assets.car
 ├── Frameworks/
 ├── Base.lproj/
 └── embedded.mobileprovision

The system reads the Info.plist to understand:

  • App identifier
  • Launch storyboard
  • Supported orientations
  • Required capabilities
  • Scene configuration

3. Security Verification

Before the app runs, iOS performs strict security checks.

Code Signing Validation

iOS verifies:

  • Apple-issued certificate
  • App signature
  • Provisioning profile
  • Binary integrity

If modified or unsigned:

  • iOS refuses execution

This is part of Apple’s secure boot chain.

4. Process Creation

After verification:

  • iOS kernel creates a new process for the app.
  • A unique sandbox is assigned.

The kernel:

  • Allocates memory
  • Creates threads
  • Maps executable code into memory
  • Sets permissions

Each app becomes an isolated process.

5. Sandbox Initialization

Every iOS app runs in a sandbox.

The sandbox restricts:

  • File access
  • Hardware access
  • Network permissions
  • Inter-process communication

Apps cannot directly access:

  • Other apps' files
  • System memory
  • Sensitive APIs

Unless explicit entitlements are granted.

6. Dynamic Loader Starts

The dynamic linker (dyld) loads required frameworks.

Examples:

  • UIKit
  • SwiftUI
  • Foundation

The loader:

  • Resolves symbols
  • Loads shared libraries
  • Initializes runtime systems

7. Swift Runtime / Objective-C Runtime Initialization

Depending on the app:

Swift Runtime

Initializes:

  • ARC (Automatic Reference Counting)
  • Metadata
  • Generics
  • Protocol dispatch
  • Concurrency runtime

Objective-C Runtime

Initializes:

  • Class registration
  • Method dispatch tables
  • Dynamic messaging

Objective-C uses:


objc_msgSend()

for dynamic method calls.

8. Entry Point Starts

Historically iOS apps started with:


UIApplicationMain()

Modern Swift apps often use:


@main
struct MyApp: App {
}

or:


@UIApplicationMain
class AppDelegate: UIResponder, UIApplicationDelegate {
}

The actual low-level entry point is still essentially:


main()

which eventually calls:


UIApplicationMain(
    argc,
    argv,
    nil,
    NSStringFromClass(AppDelegate.self)
)

UIApplicationMain() is extremely important because it:

  • Creates the application object
  • Starts the main event loop
  • Connects app delegate
  • Initializes UIKit
  • Starts handling events

9. UIApplication Object Creation

A singleton UIApplication instance is created.

Responsibilities:

  • Event handling
  • Touch delivery
  • App lifecycle
  • Background execution
  • Notifications

There is only one application object per app process.

10. App Delegate Initialization

The App Delegate becomes the central lifecycle manager.

Example:


class AppDelegate: UIResponder, UIApplicationDelegate

Important methods:


application(
    _:didFinishLaunchingWithOptions:
)

Called after launch setup.

11. Scene System Initialization (Modern iOS)

Modern iOS uses scenes.

A scene represents a UI session/window.

The system creates:


UIScene

then:


UIWindowScene

Then your:


SceneDelegate

or SwiftUI scene lifecycle starts.

12. Window Creation

The system creates:


UIWindow

The window:

  • Receives touch events
  • Hosts view hierarchy
  • Renders content

13. Root View Controller Setup

Your root controller is attached.

Example:


window.rootViewController =
    UINavigationController(
        rootViewController: HomeVC()
    )

or SwiftUI:


WindowGroup {
    ContentView()
}

14. View Hierarchy Loads

UIKit now loads:

  • Views
  • Constraints
  • Storyboards/XIBs
  • SwiftUI view trees

Lifecycle begins:


viewDidLoad()
viewWillAppear()
viewDidAppear()

15. Main Run Loop Starts

This is one of the most important concepts.

iOS starts the:


Main Run Loop

The run loop continuously waits for:

  • Touches
  • Gestures
  • Timers
  • Network callbacks
  • Rendering updates
  • System events

Simplified loop:


while app_is_running:
    wait_for_events()
    process_events()
    update_ui()

This loop runs on the main thread.

16. Event Handling System

Touch flow:


Hardware Touch
    ↓
IOKit
    ↓
SpringBoard
    ↓
UIApplication
    ↓
UIWindow
    ↓
UIView
    ↓
Responder Chain

The responder chain determines which object handles the event.

17. Rendering Pipeline

UIKit/SwiftUI do not directly draw pixels.

Rendering flow:


UIView/SwiftUI
   ↓
CALayer
   ↓
Core Animation
   ↓
Metal/OpenGL
   ↓
GPU
   ↓
Display

Core Animation

Handles:

  • Animations
  • Layer compositing
  • Smooth rendering

Metal

Modern low-level GPU API used by iOS.

Metal

18. Memory Management

iOS aggressively manages memory.

Swift uses:


ARC (Automatic Reference Counting)

Objects are automatically retained/released.

When memory pressure occurs:

  • Background apps may be suspended
  • Unused resources purged
  • App may receive warnings

Example:


didReceiveMemoryWarning()

19. Backgrounding

When user leaves app:

States change:


Active
Inactive
Background
Suspended

The app usually becomes suspended.

Suspended apps:

  • Remain in memory
  • Execute no code

20. App Termination

Apps terminate when:

  • User force quits
  • Memory pressure occurs
  • Crash happens
  • System shutdown

The process is destroyed by the kernel.

Memory/resources are reclaimed.

Important Threads

Main Thread

Handles:

  • UI
  • Events
  • Rendering coordination

Background Threads

Handle:

  • Networking
  • Database
  • Heavy computation

Blocking the main thread causes UI freezing.

Extremely Simplified Mental Model

You can think of an iOS app as:


A sandboxed process
+
Event loop
+
UI rendering tree
+
Lifecycle managed by iOS

The operating system:

  • Creates the process
  • Manages memory
  • Delivers events
  • Suspends/resumes apps
  • Protects the system
  • Renders frames through GPU pipelines

while your app mainly:

  • Defines UI
  • Responds to events
  • Manages data
  • Requests system services
