XCTest example with a “test use case”

Here’s a simple but realistic XCTest example with a “test use case” style so you can see how it’s used in practice.

Let’s say you have a Login feature and you want to test it.

🧠 1. Production Code (System Under Test)


import Foundation

struct AuthService {
    func login(username: String, password: String) -> Bool {
        return username == "admin" && password == "1234"
    }
}

🧪 2. XCTest Test Case (Unit Test)


import XCTest
@testable import YourAppModuleName

final class AuthServiceTests: XCTestCase {

    var authService: AuthService!

    override func setUp() {
        super.setUp()
        authService = AuthService()
    }

    override func tearDown() {
        authService = nil
        super.tearDown()
    }

    // MARK: - Test Case: Successful login

    func testLogin_withValidCredentials_shouldReturnTrue() {
        // Arrange
        let username = "admin"
        let password = "1234"

        // Act
        let result = authService.login(username: username, password: password)

        // Assert
        XCTAssertTrue(result, "Login should succeed with correct credentials")
    }

    // MARK: - Test Case: Failed login

    func testLogin_withInvalidCredentials_shouldReturnFalse() {
        // Arrange
        let username = "user"
        let password = "wrong"

        // Act
        let result = authService.login(username: username, password: password)

        // Assert
        XCTAssertFalse(result, "Login should fail with incorrect credentials")
    }
}

🧩 3. “Test Use Case” Style (Cleaner Architecture Example)

If you follow Clean Architecture, you usually test a Use Case, not just a service.

Use Case


struct LoginUseCase {
    let authService: AuthService

    func execute(username: String, password: String) -> Bool {
        authService.login(username: username, password: password)
    }
}

🧪 Test for Use Case


final class LoginUseCaseTests: XCTestCase {

    func testExecute_withValidCredentials_shouldSucceed() {
        // Arrange
        let authService = AuthService()
        let useCase = LoginUseCase(authService: authService)

        // Act
        let result = useCase.execute(username: "admin", password: "1234")

        // Assert
        XCTAssertTrue(result)
    }

    func testExecute_withInvalidCredentials_shouldFail() {
        // Arrange
        let authService = AuthService()
        let useCase = LoginUseCase(authService: authService)

        // Act
        let result = useCase.execute(username: "bad", password: "user")

        // Assert
        XCTAssertFalse(result)
    }
}

💡 Key XCTest Concepts Shown

  • Arrange → setup data
  • Act → call function
  • Assert → verify result
  • setUp() / tearDown() → lifecycle hooks
  • XCTAssertTrue / XCTAssertFalse → validation

The purpose of XCTest (and test use cases like the example I showed) is to automatically verify that your code behaves correctly—without you manually running the app and checking everything yourself.

🧪 In simple terms

It’s a way to answer:

“If I change my code, did I accidentally break something?”

🎯 Why this matters

1. Prevent bugs before users see them

Instead of discovering issues in production:

  • You run tests
  • Tests fail immediately if something breaks
  • You fix it before release

2. Make code changes safer (regression protection)

Example:

You update login logic.

Without tests:

  • You might unknowingly break login

With tests:

  • XCTest tells you instantly:

    “Login no longer works for valid users”

3. Confirm business logic works correctly

Your “use case” test ensures:

  • Login succeeds with correct credentials
  • Login fails with wrong credentials

So you're not just testing code—you’re testing real app behavior rules

4. Support refactoring

You can safely rewrite code like:

  • switching API layer
  • changing architecture (MVC → Clean Architecture)
  • optimizing logic

If tests still pass → behavior is still correct

5. Acts like executable documentation

Your tests describe:

“This is how the system is supposed to behave”

So other developers (or future you) can understand expected behavior quickly.

🧠 Why “Use Case” testing is special

Instead of testing low-level code:


AuthService.login()

You test higher-level behavior:


LoginUseCase.execute()

This ensures you're validating:

  • real app flows
  • not just isolated functions

🚀 Real-world analogy

Think of XCTest like:

  • 🏗️ Building inspection checklist
  • Every feature = must pass inspection before shipping
