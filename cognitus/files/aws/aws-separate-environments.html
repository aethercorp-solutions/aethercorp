AWS Separate Environments

For a Node.js + AWS Serverless application, I recommend treating Developer, UAT, and Production as separate environments, with separate configuration, databases, and ideally separate AWS resources.

A good architecture for your situation would be: 


            GitHub / Bitbucket
                │
┌───────────────┼───────────────┐
│               │               │
develop           uat             main
│               │               │
▼               ▼               ▼
DEV environment   UAT environment   PROD environment
│               │               │
┌───────┴───────┐ ┌────┴──────┐ ┌─────┴────────┐
│               │ │           │ │              │
API Gateway     | Lambda      | Lambda         API Gateway
│               │ │           │ │              │
iapi...         | MongoDB     | MongoDB        sapi...
│               │ │           │ │              │
DEV DB            UAT DB        UAT DB         PROD DB

For your existing Castanet-style setup, I would use something like:


DEV
https://iapi.thetoast.io

UAT
https://uapi.thetoast.io

PRODUCTION
https://sapi.thetoast.io

1. Separate environments

The most important rule is:

Never let your developer environment accidentally use production resources.

For example:

Environment API Database AWS Account/Resources
Developer iapi.thetoast.io castanet_dev DEV
UAT uapi.thetoast.io castanet_uat UAT
Production sapi.thetoast.io castanet_prod PROD

Ideally, you eventually use separate AWS accounts:


AWS Organization
│
├── Development Account
├── UAT Account
└── Production Account

For a smaller project, separate AWS resources inside one account can work initially.

2. Use Serverless Framework or AWS SAM

For Node.js Lambda applications, I'd strongly recommend Infrastructure as Code.

For example:


castanet-api/
│
├── src/
│   ├── handlers/
│   │   ├── auth.js
│   │   ├── contacts.js
│   │   ├── users.js
│   │   └── analytics.js
│   │
│   ├── services/
│   ├── repositories/
│   └── utils/
│
├── serverless.yml
├── package.json
├── .env.development
├── .env.uat
├── .env.production
└── .gitignore

I would personally use Serverless Framework if your goal is a relatively straightforward Lambda/API Gateway application.

3. Environment configuration

Don't hard-code things like:


const mongoUri = "mongodb+srv://production...";

Instead:


const mongoUri = process.env.MONGO_URI;

Then each environment gets its own value.

For example:

Developer


NODE_ENV=development

MONGO_DATABASE=castanet_dev

API_URL=https://iapi.thetoast.io

GOOGLE_REDIRECT_URI=https://iapi.thetoast.io/auth/google/callback

UAT


NODE_ENV=uat

MONGO_DATABASE=castanet_uat

API_URL=https://uapi.thetoast.io

GOOGLE_REDIRECT_URI=https://uapi.thetoast.io/auth/google/callback

Production


NODE_ENV=production

MONGO_DATABASE=castanet_prod

API_URL=https://sapi.thetoast.io

GOOGLE_REDIRECT_URI=https://sapi.thetoast.io/auth/google/callback

But don't put production secrets in .env.production inside Git.

Use AWS Secrets Manager or SSM Parameter Store.

4. Separate secrets from configuration

This is very important for production.

For example:


AWS Secrets Manager
│
├── /castanet/dev/mongodb
├── /castanet/uat/mongodb
├── /castanet/prod/mongodb
│
├── /castanet/dev/google
├── /castanet/uat/google
└── /castanet/prod/google

Your Lambda receives the appropriate secret.

For example:


const mongoUri = process.env.MONGO_URI;

AWS supplies:


MONGO_URI

without your source code knowing the actual password.

5. Serverless configuration

A simplified serverless.yml could look like:


service: castanet-api

provider:
  name: aws
  runtime: nodejs22.x
  region: us-east-2

  environment:
    NODE_ENV: ${sls:stage}
    MONGO_URI: ${ssm:/castanet/${sls:stage}/mongo-uri}

functions:

  api:
    handler: src/handler.handler

    events:
      - httpApi:
          path: /{proxy+}
          method: ANY

Then:


serverless deploy --stage dev

creates DEV.


serverless deploy --stage uat

creates UAT.


serverless deploy --stage prod

creates production.

6. Use different Lambda resources

You want:


castanet-api-dev
castanet-api-uat
castanet-api-prod

rather than one Lambda constantly being overwritten.

For example:


Lambda
│
├── castanet-api-dev
│
├── castanet-api-uat
│
└── castanet-api-prod

Same codebase, different deployment.

This makes it much safer.

7. API Gateway

Likewise:


API Gateway
│
├── DEV
│   └── iapi.thetoast.io
│
├── UAT
│   └── uapi.thetoast.io
│
└── PROD
    └── sapi.thetoast.io

So your React/mobile applications know which backend they're talking to.

8. MongoDB should also be separated

Since your application uses MongoDB, don't have this:


DEV ──────┐
UAT ──────┼──> production MongoDB
PROD ─────┘

That's dangerous.

Instead:


DEV ──> castanet_dev

UAT ──> castanet_uat

PROD ──> castanet_prod

Even better:


MongoDB Atlas
│
├── DEV cluster
├── UAT cluster
└── PROD cluster

For smaller applications, you can initially use separate databases within a cluster:


castanet_dev
castanet_uat
castanet_prod

but production isolation is preferable as the system grows.

9. Git branches

I'd structure your Git workflow like this:


feature/*
     │
     ▼
 develop
     │
     ▼
    UAT
     │
     ▼
   main
     │
     ▼
 PRODUCTION

Example:


git checkout -b feature/add-contacts

Develop:


feature/add-contacts
        ↓
     develop
        ↓
       DEV

When ready:


develop
   ↓
 UAT

After UAT approval:


uat
 ↓
main
 ↓
PRODUCTION

You don't necessarily need a permanent uat branch; many teams use:


        feature → develop → main
             │
             └── UAT deployment

I actually prefer this simpler approach.

11. Don't use AWS access keys in GitHub

This is another important production practice.

Avoid:


AWS_ACCESS_KEY_ID=xxxxx
AWS_SECRET_ACCESS_KEY=xxxxx

inside GitHub secrets if you can avoid it.

Use GitHub OIDC → AWS IAM Role.

Architecture:


GitHub Actions
       │
       │ OIDC
       ▼
AWS IAM Role
       │
       ▼
Lambda / API Gateway / S3 / etc.

Then GitHub receives temporary AWS credentials.

Much safer than permanent access keys.

13. Configuration object in Node.js

I recommend centralizing environment configuration.

For example:


const config = {
    environment: process.env.NODE_ENV,
    
    mongo: {
        uri: process.env.MONGO_URI,
        database: process.env.MONGO_DATABASE
    },
    
    google: {
        clientId: process.env.GOOGLE_CLIENT_ID,
        clientSecret: process.env.GOOGLE_CLIENT_SECRET,
        redirectUri: process.env.GOOGLE_REDIRECT_URI
    },
    
    jwt: {
        secret: process.env.JWT_SECRET
    }
};

module.exports = config;

Then:


const config = require('./config');

await connectMongo(
  config.mongo.uri,
  config.mongo.database
);

This prevents environment-specific logic from being scattered throughout the application.

15. Logging

Don't mix logs between environments.

Use CloudWatch log groups such as:


/aws/lambda/castanet-api-dev
/aws/lambda/castanet-api-uat
/aws/lambda/castanet-api-prod

Then you can immediately answer:

Is this a production problem or a UAT problem?

For production, I would also add:

  • CloudWatch alarms
  • Lambda error alarms
  • API Gateway 5xx alarms
  • latency monitoring
  • AWS X-Ray/OpenTelemetry where appropriate
  • centralized structured JSON logging

Example:


console.log(JSON.stringify({
    level: "info",
    event: "contact_created",
    userId,
    environment: process.env.NODE_ENV
}));

16. IAM permissions

Don't give your Lambda:


AdministratorAccess

Instead:


DEV Lambda
 ├── DEV Secrets
 ├── DEV S3
 └── DEV resources

UAT Lambda
 ├── UAT Secrets
 ├── UAT S3
 └── UAT resources

PROD Lambda
 ├── PROD Secrets
 ├── PROD S3
 └── PROD resources

Use least privilege.

17. S3 should be separated too

If your application uploads files:


castanet-dev-assets
castanet-uat-assets
castanet-prod-assets

rather than:


castanet-assets

with everything mixed together.

19. The most important principle

Think of the environments as three completely different systems:

DEV


Code changes
↓
Fast deployment
↓
Developer testing
↓
Can break

UAT


Release candidate
↓
QA/business testing
↓
Production-like configuration
↓
Should be stable

PROD


Approved release
↓
Real users
↓
Real data
↓
Maximum protection

So the deployment pipeline becomes:


FEATURE
   │
   ▼
DEVELOP
   │
   ▼
 DEV AWS
   │
   ▼
 QA / UAT
   │
   ▼
 APPROVAL
   │
   ▼
 MAIN
   │
   ▼
 PROD AWS

What I would use for your stack

Given your existing Node.js + Lambda + API Gateway + MongoDB + Firebase/Auth + Google OAuth + GitHub Actions background, a solid modern stack would be:

Node.js 22 + Serverless Framework + Lambda + API Gateway HTTP API + MongoDB Atlas + Secrets Manager/SSM + CloudWatch + GitHub Actions + AWS IAM/OIDC + separate DEV/UAT/PROD resources.

That gives you a production architecture that is also a very good foundation for moving toward Senior/Staff Engineer or Systems Architect responsibilities.
