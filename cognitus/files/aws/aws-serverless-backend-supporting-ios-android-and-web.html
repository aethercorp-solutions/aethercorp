AWS Serverless backend supporting iOS, Android, and Web

For an AWS Serverless backend supporting iOS, Android, and Web, the cleanest approach is to separate platform authentication from your application authentication.

Recommended architecture

                │      / Web       │
                └────────┬─────────┘

                Platform Login
              Google / Apple / etc.

The important idea is:

Google/Apple tokens authenticate the user initially. Your own JWT authenticates the user to your API afterward.

1. Use one application JWT

Don't create completely different authentication systems for iOS, Android, and Web.

Have your backend issue one application access token:


POST /auth/login
POST /auth/refresh
POST /auth/logout

The JWT can contain:


{
    "sub": "user-id",
    "email": "user@example.com",
    "platform": "ios",
    "sessionId": "abc123",
    "iat": 1755910000,
    "exp": 1755913600
}

The platform is useful for logging and platform-specific behavior, but don't use it as the primary security mechanism.

2. Platform-specific login

Your clients can have different authentication mechanisms.

iOS

For example:


iOS
 ↓
Google Sign-In / Apple Sign-In
 ↓
authorization code / identity token
 ↓
POST /auth/login
 ↓
AWS Lambda
 ↓
verify with Google/Apple
 ↓
find/create user
 ↓
issue your JWT

Android


Android
 ↓
Google Sign-In
 ↓
authorization code / ID token
 ↓
POST /auth/login
 ↓
AWS Lambda
 ↓
verify Google
 ↓
issue your JWT

Web


Browser
 ↓
Google OAuth
 ↓
authorization code
 ↓
POST /auth/login
 ↓
AWS Lambda
 ↓
exchange + verify code
 ↓
issue your JWT

The backend should ultimately decide whether the authentication is valid.

3. Don't trust the client-provided platform

Avoid doing this:


const platform = req.body.platform;

if (platform === "ios") {
    // trust request
}

A client can simply send:


{
    "platform": "ios"
}

Instead, use platform as metadata.

For example:


const platform = req.headers["x-platform"];

and validate it:


const allowedPlatforms = ["ios", "android", "web"];

if (!allowedPlatforms.includes(platform)) {
    throw new Error("Invalid platform");
}

But even then, don't use it as proof of identity.

4. Separate identity from session

This is probably the most important design decision for your system.

Your database should have something conceptually like:


User
 ├── _id
 ├── email
 ├── name
 └── providers
      ├── google
      │    └── providerUserId
      └── apple
           └── providerUserId

And separately:


Session
 ├── sessionId
 ├── userId
 ├── platform
 ├── refreshTokenHash
 ├── deviceId
 ├── createdAt
 ├── expiresAt
 └── revokedAt

This lets the same person log in from:


iPhone
Android
Mac
Windows

without creating four different users.

5. Use refresh tokens for long-lived sessions

A good flow is:


ACCESS TOKEN
short lifetime
     │
     │ expires
     ▼
REFRESH TOKEN
longer lifetime
     │
     ▼
POST /auth/refresh
     │
     ▼
new ACCESS TOKEN

For example:


Access JWT:   15 minutes
Refresh token: 30–90 days

You can adjust these according to your security requirements.

Your client stores:


interface TokenStorage {
    accessToken: string;
    refreshToken: string;
    expirationDate: number;
    userId: string;
    platform: "ios" | "android" | "web";
    sessionId: string;
}

6. Your API should have two types of middleware

Normal API


Authorization: Bearer <access_token>

Lambda middleware:


verifyApplicationJWT()

If valid:


request.user
   ↓
Lambda handler

If expired:


401

Refresh endpoint

This is different.


POST /auth/refresh

The refresh endpoint should not require a non-expired access JWT.

Instead:


refresh token
     ↓
find session
     ↓
verify refresh token
     ↓
verify session isn't revoked
     ↓
issue new access JWT

This directly addresses the issue you've been working on where your expired JWT was being rejected before /refresh-token could execute.

7. Don't use an expired access JWT as the refresh credential

This is a common mistake.

Bad:


expired JWT
    +
refresh endpoint
    ↓
decode JWT
    ↓
trust user

Better:


refreshToken
     ↓
hash
     ↓
find session
     ↓
verify
     ↓
userId
     ↓
new JWT

The refresh token should be the credential that authorizes the refresh.

8. Axios / React Native flow

Your client can automatically refresh:


API request
    │
    ▼
access JWT
    │
    ├── valid ───────────────► API
    │
    └── expired / 401
             │
             ▼
       /auth/refresh
             │
             ▼
       new access JWT
             │
             ▼
       retry original request

For example:


try {
    return await api.request(config);
} catch (error) {

    if (error.response?.status === 401) {

        const newToken = await refreshAccessToken();

        if (newToken) {
            config.headers.Authorization =
                `Bearer ${newToken}`;

            return api.request(config);
        }
    }

    throw error;
}

However, you should also prevent multiple simultaneous refresh calls.

For example, if five API requests return 401 simultaneously:


                Request A ─┐
Request B ─┤
Request C ─┼──► ONE refresh request
Request D ─┤
Request E ─┘
                 │
                 ▼
             new token
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
        A        B        C...

This is especially important in React Native.

9. AWS Serverless structure

I'd structure your Lambda functions approximately like this:


src/
├── auth/
│   ├── auth.controller.ts
│   ├── auth.service.ts
│   ├── auth.middleware.ts
│   ├── token.service.ts
│   ├── session.service.ts
│   │
│   ├── providers/
│   │   ├── google.provider.ts
│   │   ├── apple.provider.ts
│   │   └── provider.interface.ts
│   │
│   └── handlers/
│       ├── login.ts
│       ├── refresh.ts
│       ├── logout.ts
│       └── me.ts
│
├── users/
│   ├── user.service.ts
│   └── user.model.ts
│
└── middleware/
    └── requireAuth.ts

Then your provider interface can be consistent:


interface AuthProvider {
    verifyToken(token: string): Promise<{
        providerUserId: string;
        email?: string;
        name?: string;
    }>;
}

Google:


class GoogleProvider implements AuthProvider {
    async verifyToken(token: string) {
        // Google verification
    }
}

Apple:


class AppleProvider implements AuthProvider {
    async verifyToken(token: string) {
        // Apple verification
    }
}

Then:


const provider = getProvider(providerName);

const identity = await provider.verifyToken(token);

Your application authentication doesn't need to care whether the user came from Google or Apple.

The key rule

Platform authentication ≠ application authentication.

Google/Apple authenticate the identity. Your AWS backend establishes the application's session. Your application JWT protects your API. The refresh token maintains the session.

For your existing implementation, I would specifically refactor your current verifyApplicationJWT, userTokenMustExist, userMustExistForRefresh, and refreshToken flow so that expired access JWTs are allowed only through /auth/refresh, while every normal API remains protected by a non-expired JWT.
