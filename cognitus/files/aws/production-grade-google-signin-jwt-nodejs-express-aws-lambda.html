Production-grade Google Sign-In + JWT

For a production-grade Google Sign-In + JWT + Node.js + Express + AWS Lambda/API Gateway, I would separate the responsibilities like this:

1. Recommended architecture 


                ┌──────────────────┐
                │   iOS / Android  │
                │    React / Web   │
                └────────┬─────────┘
                         │
                         │ Google Sign-In
                         ▼
                ┌──────────────────┐
                │      Google      │
                │   OAuth / OIDC   │
                └────────┬─────────┘
                         │
                Google ID Token
                         │
                         ▼
┌──────────────────────────────────────────────────────┐
│                  AWS API Gateway                     │
└───────────────────────┬──────────────────────────────┘
                    │
                    ▼
          ┌─────────────────────┐
          │    AWS Lambda       │
          │    Express App      │
          └─────────┬───────────┘
                    │
          1. Verify Google ID Token
                    │
                    ▼
          ┌─────────────────────┐
          │      MongoDB        │
          │                     │
          │ googleSub           │
          │ email               │
          │ userId              │
          └─────────┬───────────┘
                    │
             Create own JWT
                    │
                    ▼
          Access Token + Refresh Token
                    │
                    ▼
             Client Application

The important concept is:

Google's token authenticates the user with Google. Your application's JWT authenticates the user with your API.

Google specifically recommends sending the Google ID token to your backend and verifying it there rather than trusting a user ID supplied by the client.

2. Don't do this

A common implementation is:


Client
   ↓
Google ID Token
   ↓
Backend
   ↓
decode JWT
   ↓
trust email

That's not sufficient.

Never do:


const payload = jwt.decode(token);

const email = payload.email;

// Trust email

decode() does not prove that Google signed the token.

Instead:


Google ID Token
       ↓
Google Auth Library
       ↓
verify signature
       ↓
verify aud
       ↓
verify iss
       ↓
verify exp
       ↓
trusted Google identity

Google recommends google-auth-library and verifyIdToken() for production Node.js implementations.

5. Environment variables

Don't hard-code secrets.

JWT_ISSUER=your-api

JWT_ACCESS_SECRET=very-long-random-secret
JWT_REFRESH_SECRET=another-very-long-random-secret

In AWS, production secrets should preferably be managed through AWS Secrets Manager or Parameter Store, rather than committed to Git.

6. Google verification service

services/google.service.js


const { OAuth2Client } = require("google-auth-library");

const googleClient = new OAuth2Client(
    process.env.GOOGLE_CLIENT_ID
);

exports.verifyGoogleIdToken = async (idToken) => {

    if (!idToken) {
        throw new Error("Google ID token is required");
    }

    const ticket = await googleClient.verifyIdToken({
        idToken,
        audience: process.env.GOOGLE_CLIENT_ID
    });

    const payload = ticket.getPayload();

    if (!payload) {
        throw new Error("Invalid Google ID token");
    }

    if (!payload.sub) {
        throw new Error("Google account ID missing");
    }

    if (!payload.email) {
        throw new Error("Google email missing");
    }

    if (payload.email_verified !== true) {
        throw new Error("Google email is not verified");
    }

    return {
        googleSub: payload.sub,
        email: payload.email,
        name: payload.name,
        picture: payload.picture
    };
};

This is important because Google's verification checks the JWT signature plus important claims such as aud, iss, and exp.

7. Your JWT service

After Google authentication succeeds, your server creates its own JWT.

services/jwt.service.js


const jwt = require("jsonwebtoken");
const crypto = require("crypto");

exports.createAccessToken = (user) => {

    return jwt.sign(
        {
            sub: user.id,
            email: user.email,
            tokenType: "access"
        },
        process.env.JWT_ACCESS_SECRET,
        {
            algorithm: "HS256",
            expiresIn: "15m",
            issuer: process.env.JWT_ISSUER,
            audience: process.env.JWT_AUDIENCE,
            jwtid: crypto.randomUUID()
        }
    );
};

exports.createRefreshToken = (user) => {

    return jwt.sign(
        {
            sub: user.id,
            tokenType: "refresh"
        },
        process.env.JWT_REFRESH_SECRET,
        {
            algorithm: "HS256",
            expiresIn: "30d",
            issuer: process.env.JWT_ISSUER,
            audience: process.env.JWT_AUDIENCE,
            jwtid: crypto.randomUUID()
        }
    );
};

So you have:


Google JWT
     │
     │ verify
     ▼
Google identity
     │
     │ find/create user
     ▼
Your User ID
     │
     ├── Access JWT   → 15 minutes
     │
     └── Refresh JWT  → 30 days

8. Google login controller

controllers/auth.controller.js


const {
    verifyGoogleIdToken
} = require("../services/google.service");

const {
    createAccessToken,
    createRefreshToken
} = require("../services/jwt.service");

exports.googleLogin = async (req, res, next) => {

    try {

        const { idToken } = req.body;

        if (!idToken) {
            return res.status(400).json({
                message: "Google ID token is required"
            });
        }

        // 1. Verify Google's token
        const googleUser =
            await verifyGoogleIdToken(idToken);

        // 2. Find or create your application user
        let user = await User.findOne({
            googleSub: googleUser.googleSub
        });

        if (!user) {

            user = await User.create({
                googleSub: googleUser.googleSub,
                email: googleUser.email,
                name: googleUser.name,
                picture: googleUser.picture,
                provider: "google"
            });
        }

        // 3. Create YOUR tokens
        const accessToken =
            createAccessToken(user);

        const refreshToken =
            createRefreshToken(user);

        // 4. Return your application's authentication
        return res.status(200).json({

            user: {
                id: user.id,
                email: user.email,
                name: user.name,
                picture: user.picture
            },

            accessToken,

            refreshToken

        });

    } catch (error) {

        console.error("Google login failed:", error);

        return next(error);
    }
};

9. Important: use Google's sub

Your MongoDB user should ideally have something like:


{
    _id: ObjectId("..."),

    googleSub: "103xxxxxxxxxxxxxxxx",

    email: "user@gmail.com",

    name: "John Doe",

    provider: "google"
}

Don't make email your permanent Google identity.

Google explicitly recommends using the Google ID token's sub claim as the unique Google account identifier.

So:


googleSub
   ↓
Google identity

while:


email
   ↓
profile/contact information

10. JWT authentication middleware

Now all protected APIs use your JWT, not the Google token.

middleware/authenticate.js


const jwt = require("jsonwebtoken");

module.exports = (req, res, next) => {

    try {

        const authorization =
            req.headers.authorization;

        if (!authorization) {
            return res.status(401).json({
                message: "Authorization header required"
            });
        }

        const [scheme, token] =
            authorization.split(" ");

        if (scheme !== "Bearer" || !token) {
            return res.status(401).json({
                message: "Invalid authorization format"
            });
        }

        const payload = jwt.verify(
            token,
            process.env.JWT_ACCESS_SECRET,
            {
                algorithms: ["HS256"],
                issuer: process.env.JWT_ISSUER,
                audience: process.env.JWT_AUDIENCE
            }
        );

        if (payload.tokenType !== "access") {
            return res.status(401).json({
                message: "Invalid token type"
            });
        }

        req.user = {
            id: payload.sub,
            email: payload.email
        };

        next();

    } catch (error) {

        if (error.name === "TokenExpiredError") {
            return res.status(401).json({
                message: "Access token expired"
            });
        }

        return res.status(401).json({
            message: "Invalid access token"
        });
    }
};

16. Refresh token flow

When access token expires:


Client
   │
   │ POST /auth/refresh
   │ refreshToken
   ▼
Lambda
   │
   ▼
verify refresh JWT
   │
   ▼
check refresh token in DB
   │
   ▼
generate new access JWT
   │
   ▼
Client

For a stronger production implementation, I would not treat a long-lived JWT refresh token as sufficient by itself. Store a hashed refresh-token/session identifier server-side and implement rotation + revocation.

For example:


{
    _id: "...",

    userId: "...",

    tokenHash: "...",

    deviceId: "...",

    platform: "ios",

    expiresAt: "...",

    revokedAt: null,

    createdAt: "...",

    lastUsedAt: "..."
}

This is particularly useful for your existing device-token/user-token architecture.

17. Even better: use asymmetric JWTs

For a larger production system, I would consider:


RS256 / ES256

instead of:


HS256

Architecture:


            JWT PRIVATE KEY
                │
                ▼
           Auth Service
                │
                │ signs
                ▼
             JWT
                │
   ┌────────────┼────────────┐
   ▼            ▼            ▼
API #1       API #2       API #3
   │            │            │
   └────────────┼────────────┘
                │
          PUBLIC KEY
          verifies JWT

This is useful when multiple services need to verify your JWT without sharing your signing secret.

18. API Gateway JWT authorizer

For an even more AWS-native architecture, you can move JWT verification out of Express.


Client
  │
  ▼
API Gateway
  │
  │ JWT Authorizer
  │
  ├── INVALID → 401
  │
  └── VALID
       │
       ▼
     Lambda
       │
       ▼
    Express

Then Lambda doesn't need to verify the JWT on every request.

However, there's an important distinction:

Google ID-token verification still belongs in your login flow.


POST /auth/google

Google ID Token
      ↓
Lambda
      ↓
google-auth-library
      ↓
verify Google token
      ↓
issue application JWT

Then:


GET /users/profile

Application JWT
      ↓
API Gateway JWT Authorizer
      ↓
Lambda
      ↓
Express

That is a very clean architecture for AWS.

19. What I would use for your application

Given your existing Node.js + Express + Lambda + MongoDB + Google Sign-In architecture, I'd use:

Component Recommendation
Google authentication Google Identity Services
Google token verification google-auth-library
Google identity sub
Application authentication Your own JWT
Access JWT ~15 minutes
Refresh token Rotation + server-side session
JWT algorithm RS256/ES256 for larger systems
API Gateway HTTP API
Protected API API Gateway JWT Authorizer
Business authorization Express middleware/service
User database MongoDB
Refresh sessions MongoDB/Redis
Secrets AWS Secrets Manager
Runtime AWS Lambda
Web framework Express
Lambda adapter serverless-http

Google's current guidance explicitly recommends server-side verification of the ID token and using sub as the stable Google account identifier.

The key distinction


        AUTHENTICATION
                │
                ▼
      Google ID Token
                │
          "Who is this?"
                │
                ▼
         Your User ID
                │
                ▼
           YOUR JWT
                │
          "Can they use
           my API?"
                │
                ▼
       API Gateway / Lambda

So Google OAuth ≠ your application's JWT.

Google proves the user's identity. Your backend establishes the application's authenticated session and authorization model.

If you're upgrading the signInWithGoogle implementation you showed earlier, this is the architecture I would move it toward, rather than simply adding jwt.sign() to the existing controller.
