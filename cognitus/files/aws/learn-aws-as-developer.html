Learn AWS as a developer

If you're coming from a traditional architecture like:

Frontend → Backend Server → Database

the easiest way to learn AWS as a developer is to learn how AWS replaces each part of that architecture.

1. Start with the traditional architecture

Imagine you build an application like this:


    React / Mobile App
        ↓
     REST API
        ↓
   Node.js Server
        ↓
     MongoDB

Traditionally, you might have:

  • One physical/virtual server
  • Nginx
  • Node.js
  • Database server
  • Manual deployment
  • Server monitoring
  • Manual scaling

You need to worry about:


Server CPU
RAM
Disk
OS updates
Backups
Networking
Scaling
SSL
Load balancing

AWS changes the way you think about these components.

2. Learn AWS by mapping old → cloud

This is the most important concept.

Traditional AWS
Physical server EC2
Virtual machine EC2
Nginx ALB / CloudFront
Node.js server EC2 / Lambda
REST API API Gateway
File storage S3
MySQL/PostgreSQL server RDS
MongoDB server MongoDB Atlas / DocumentDB
Redis server ElastiCache
Load balancer Application Load Balancer
DNS Route 53
CDN CloudFront
SSL certificate ACM
Background jobs SQS
Pub/sub SNS
Logs CloudWatch
User authentication Cognito
Secrets/config Secrets Manager / Parameter Store
Containers ECS / Fargate
Kubernetes EKS

Don't try to memorize all of these initially.

4. Phase 1 — AWS fundamentals

First understand:

Regions

AWS has physical geographic locations:


us-east-1
us-west-2
ap-southeast-1
ap-northeast-1

For example:


Philippines
    ↓
ap-southeast-1
    ↓
Singapore

You don't need to memorize every region.

Understand:

A region is a geographic AWS location containing AWS infrastructure.

Availability Zones

A region contains multiple isolated locations.


Singapore Region
       |
 ┌─────┼─────┐
 AZ-a  AZ-b  AZ-c

This helps AWS applications survive infrastructure failures.

5. Phase 2 — IAM

Learn IAM early.

IAM controls:


WHO can access
WHAT they can access
WHAT they can do

Example:


Developer
   ↓
IAM
   ↓
Can deploy Lambda
Can read S3
Cannot delete production database

Learn:

  • Users
  • Groups
  • Roles
  • Policies
  • Access keys
  • Least privilege

Especially understand IAM Roles.

For example:


Lambda
   ↓
IAM Role
   ↓
Read S3

You don't want to put AWS passwords inside your code.

6. Phase 3 — EC2

EC2 is probably the easiest bridge from traditional development to AWS.

Think:

EC2 = renting a server from AWS.

Traditional:


Buy server
     ↓
Install Ubuntu
     ↓
Install Node.js
     ↓
Install Nginx
     ↓
Deploy application

AWS:


EC2
 ↓
Ubuntu
 ↓
Node.js
 ↓
Nginx
 ↓
Your application

Learn:

  • Launch EC2
  • SSH
  • Security Groups
  • Elastic IP
  • EBS
  • Install Node.js
  • Deploy a REST API

Practical project

Deploy:


React
  ↓
EC2
  ↓
Node.js Express
  ↓
MongoDB Atlas

This teaches you the cloud version of what you already know.

7. Phase 4 — S3

S3 is extremely important.

Think:

S3 = cloud object/file storage.

Traditional:


Server
 └── uploads/
      ├── image.jpg
      ├── resume.pdf
      └── document.pdf

AWS:


Application
     ↓
    S3
     ↓
 ┌───────┐
 │ files │
 └───────┘

Learn:

  • Buckets
  • Objects
  • Permissions
  • Bucket policies
  • Pre-signed URLs
  • Static website hosting
  • Lifecycle rules

A very common architecture is:


React
  ↓
API
  ↓
S3

For uploads:


React
  ↓
Request upload URL
  ↓
API
  ↓
Pre-signed S3 URL
  ↓
S3

The file doesn't even need to pass through your backend.

8. Phase 5 — Databases

Now learn AWS database services.

RDS

For relational databases:


Node.js
   ↓
RDS
   ↓
PostgreSQL

Instead of:


Node.js
   ↓
Your own PostgreSQL server

AWS manages much of the infrastructure.

Learn:

  • PostgreSQL/MySQL
  • Backups
  • Multi-AZ
  • Security Groups
  • Encryption
  • Database credentials

DynamoDB

Then learn DynamoDB.

Think:

DynamoDB = AWS-native NoSQL database.

Traditional:


MongoDB

AWS-native:


DynamoDB

Don't learn DynamoDB before understanding basic database concepts.

9. Phase 6 — VPC

This is where many developers start getting confused.

Don't rush it.

Think of VPC as:

Your private network inside AWS.

Traditional:


Internet
   ↓
Router
   ↓
Private Network
   ↓
Servers

AWS:


Internet
    ↓
 Internet Gateway
    ↓
   VPC
 ┌───────────────┐
 │ Public subnet │
 │               │
 │ Private subnet│
 └───────────────┘

Learn these concepts:


VPC
Subnet
Route Table
Internet Gateway
NAT Gateway
Security Group
Network ACL

The most important distinction initially:

Public subnet

Can communicate directly with the internet.

Private subnet

Normally does not accept direct inbound internet traffic.

For example:


Internet
   ↓
Load Balancer
   ↓
Private EC2
   ↓
Database

That's a common production architecture.

10. Phase 7 — API Gateway + Lambda

Now you move from server-based architecture to serverless architecture.

Traditional:


React
  ↓
Node.js server
  ↓
MongoDB

Serverless:


React
  ↓
API Gateway
  ↓
Lambda
  ↓
MongoDB

Lambda

Think:

Lambda = run my function without managing a server.

Instead of:


EC2
 └── Node.js
      └── Express
           └── API

you can have:


Lambda
 └── getUsers()

AWS handles the underlying server.

11. Understand API Gateway

API Gateway exposes your Lambda functions as HTTP APIs.

For example:


GET /users
       ↓
API Gateway
       ↓
Lambda
       ↓
MongoDB

Your React application simply calls:


GET https://api.example.com/users

Learn:

  • REST APIs
  • HTTP APIs
  • Routes
  • Methods
  • CORS
  • Authentication
  • Authorizers
  • Throttling

12. Phase 8 — CloudWatch

Traditional server:


/var/log/app.log

AWS:


Application
     ↓
CloudWatch Logs

Learn:

  • Logs
  • Metrics
  • Alarms
  • Lambda logs
  • API Gateway logs
  • EC2 monitoring

For example:


Lambda error
     ↓
CloudWatch
     ↓
Alarm
     ↓
Notification

This is essential for production development.

13. Phase 9 — SQS

Now learn asynchronous architecture.

Traditional:


API
 ↓
Process everything
 ↓
Response

Problem:


10,000 tasks
     ↓
API becomes slow

AWS:


API
 ↓
SQS
 ↓
Lambda workers
 ↓
Process tasks

SQS is essentially:

A queue where work waits to be processed.

Example:


User uploads PDF
       ↓
API
       ↓
SQS
       ↓
Lambda
       ↓
Process PDF
       ↓
Database

Very useful for scalable systems.

14. Phase 10 — CloudFront

CloudFront is AWS's CDN.

Traditional:


User
 ↓
Your server
 ↓
Image

CloudFront:


                ┌── CloudFront ── User
                │
  S3 ───────────┤
                │
                └── CloudFront ── User

It caches content closer to users.

For a React application:


React build
    ↓
S3
    ↓
CloudFront
    ↓
Users

This is a very common architecture.

15. Phase 11 — Docker + ECS

After understanding EC2 and Lambda, learn containers.

Traditional:


EC2
 ↓
Node.js
 ↓
Application

Docker:


Docker container
 ├── Node.js
 ├── dependencies
 └── application

Then AWS:


Docker
   ↓
ECS
   ↓
Fargate

Think:

ECS = AWS manages containers for you.

Fargate lets you run containers without managing the underlying servers yourself.

16. Phase 12 — CI/CD

Once you understand deployment, learn automation.

Traditional:


Developer
   ↓
git push
   ↓
SSH server
   ↓
git pull
   ↓
npm install
   ↓
restart

CI/CD:


Developer
   ↓
GitHub
   ↓
CI/CD
   ↓
Build
   ↓
Test
   ↓
Deploy
   ↓
AWS

Learn:

  • GitHub Actions
  • AWS CodeBuild
  • CodeDeploy
  • CodePipeline
  • Deployment strategies

You don't need to master every AWS CI/CD service. GitHub Actions + AWS is already extremely useful.

17. Eventually learn this architecture

A very useful target for you would be:


                Internet
                │
                ▼
           CloudFront
           /         \
          /           \
         ▼             ▼
      S3            API Gateway
   React App             │
                         ▼
                       Lambda
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       MongoDB         S3             SQS
          │                             │
          │                             ▼
          │                           Lambda
          │
          ▼
      Application

This is much closer to modern cloud architecture than simply putting everything on an EC2 server.

The biggest mindset change

Don't think:

"I need to learn 100 AWS services."

Think:

"I need to understand how AWS replaces the infrastructure I used to manage myself."

For example:


OLD WORLD

Server
 ├── OS
 ├── Nginx
 ├── Node.js
 ├── App
 └── Logs

becomes:


AWS WORLD

CloudFront
     ↓
API Gateway
     ↓
Lambda
     ↓
Database
     
CloudWatch → Logs
IAM        → Security
S3         → Files
SQS        → Background work

Once you understand that mapping, AWS becomes much easier to learn.

And given your existing React + Node.js + MongoDB + Lambda + API Gateway experience, you're actually already partway through this path. The main gap is likely understanding AWS networking, IAM, deployment, security, and production architecture, rather than learning programming from scratch.
