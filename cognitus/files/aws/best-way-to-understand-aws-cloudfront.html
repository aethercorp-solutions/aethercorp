AWS CloudFront

Absolutely. The best way to understand AWS CloudFront is to build a tiny real application and put CloudFront in front of it.

1. First, understand the concept

Think of CloudFront as a delivery layer between your users and your server.

Without CloudFront:


User
  |
  | HTTPS request
  v
AWS Server
  |
  v
Your application

With CloudFront:


                AWS CloudFront
                /       |       \
               /        |        \
          User A      User B    User C
             |           |          |
             +-----------+----------+
                         |
                         v
                   Your Server

CloudFront has servers called edge locations around the world.

For example:


User in Philippines
       |
       v
CloudFront Manila/nearby edge
       |
       | cache miss
       v
AWS Origin

If CloudFront already has the requested file:


User
 |
 v
CloudFront
 |
 | CACHE HIT
 v
file returned immediately

The origin doesn't need to be contacted.

2. Our practical project

Let's make a very simple website:


my website
│
├── index.html
├── style.css
└── logo.png

We'll put these files in:

Amazon S3

Then:


Browser
   ↓
CloudFront
   ↓
S3

This is one of the easiest ways to learn CloudFront.

3. Step 1 — Create an S3 bucket

Go to:

AWS Console → S3 → Create bucket

Create something like:


my-cloudfront-demo-2026

The bucket name must be globally unique.

For this tutorial, you can keep the bucket private.

That's actually a good way to understand CloudFront because CloudFront can retrieve the files on behalf of users.

4. Step 2 — Create your website

Create index.html:


<!DOCTYPE html>
<html>
<head>
    <title>CloudFront Demo</title>
    <link rel="stylesheet" href="style.css">
</head>
<body>

    <h1>Hello CloudFront!</h1>

    <p>This website is being delivered through AWS CloudFront.</p>

</body>
</html>

Create style.css:


body {
    font-family: Arial;
    text-align: center;
    margin-top: 100px;
}

h1 {
    font-size: 50px;
}

Upload both files to your S3 bucket.

Your S3 structure becomes:


my-cloudfront-demo-2026
│
├── index.html
└── style.css

5. Step 3 — Create CloudFront distribution

Go to:

AWS Console → CloudFront → Create distribution

The important concept here is:

Origin

CloudFront asks:

"Where should I get the files from?"

Choose your S3 bucket.

So:


CloudFront
     |
     v
S3 bucket

For the origin, select your S3 bucket.

6. Step 4 — Understand the Origin

This is one of the most important CloudFront concepts.

Origin = the original source of your content.

For example:


CloudFront
    |
    +---- S3

S3 is your origin.

But CloudFront can also use:


CloudFront
    |
    +---- EC2

or:


CloudFront
    |
    +---- Application Load Balancer

or:


CloudFront
    |
    +---- API Gateway

or even:


CloudFront
    |
    +---- Your Node.js server

So don't think:

CloudFront = S3

Instead think:

CloudFront = delivery layer in front of an origin.

7. Step 5 — Configure the S3 origin securely

For a real application, don't simply make everything publicly accessible.

CloudFront supports Origin Access Control (OAC).

Conceptually:


User
  |
  v
CloudFront
  |
  | authenticated request
  v
Private S3 bucket

The user cannot directly access the S3 objects.

This is much better:


                ┌──────────────┐
                │ CloudFront   │
                └──────┬───────┘
                       |
                       v
                 Private S3

Instead of:


User ───────────────→ Public S3

8. Step 6 — Default root object

In CloudFront settings, set:


Default root object:

index.html

This means when someone visits:


https://xxxxx.cloudfront.net/

CloudFront knows to request:


/index.html

from S3.

9. Step 7 — Deploy

Create the distribution.

AWS will give you something like:


d123456abcdef.cloudfront.net

Visit:


https://d123456abcdef.cloudfront.net

You should see:


Hello CloudFront!

This website is being delivered through AWS CloudFront.

Congratulations — you've just used CloudFront. 🎉

10. Now understand what actually happened

Suppose you visit:


https://d123456abcdef.cloudfront.net/index.html

First request

CloudFront doesn't have the file yet.


Browser
   |
   v
CloudFront
   |
   | MISS
   v
S3
   |
   | index.html
   v
CloudFront
   |
   v
Browser

This is called a:

Cache Miss

11. Second request

You refresh the page.

CloudFront may already have:


index.html

cached.

So:


Browser
   |
   v
CloudFront
   |
   | HIT
   v
Browser

S3 isn't contacted.

This is a:

Cache Hit

That's the fundamental idea of CloudFront.

12. Try the most useful experiment

Change your index.html.

For example:


<h1>Hello CloudFront V2!</h1>

Upload the new file to S3.

Then immediately visit CloudFront again.

You may still see:


Hello CloudFront!

Why?

Because CloudFront has the old cached version.

This is where an important CloudFront concept appears:

Cache invalidation

You can tell CloudFront:

"Forget the cached version."

Go to:

CloudFront → Your Distribution → Invalidations

Create an invalidation:


/*

This means:

invalidate all cached files.

Then reload the CloudFront URL.

Now you should see:


Hello CloudFront V2!

13. This is why CloudFront is useful

Imagine your website has:


index.html
style.css
app.js
logo.png
video.mp4

And you have users in:


Philippines
Japan
Singapore
USA
Europe

Without CloudFront:


Philippines ───────┐
Japan ─────────────┤
Singapore ─────────┤
USA ───────────────┤──→ Origin
Europe ────────────┘

Lots of requests go to the origin.

With CloudFront:


                CloudFront
                /      |      \
               /       |       \
        Philippines   Japan    USA
               \       |       /
                \      |      /
                     Origin

CloudFront caches frequently requested content closer to users.

16. The 5 CloudFront concepts you should learn

Don't try to memorize every AWS setting initially.

Focus on these five:

1. Distribution

Your CloudFront configuration.


        CloudFront Distribution
        |
        +---- Origin
        +---- Cache behavior
        +---- SSL
        +---- Domains

Think:

"My CloudFront setup."

2. Origin

Where CloudFront gets the content.

Examples:


S3
EC2
ALB
API Gateway
external HTTP server

3. Edge location

Where CloudFront delivers/caches content close to users.

Think:

"Nearby CloudFront server."

4. Cache

CloudFront stores frequently requested content.


Request
   ↓
CloudFront
   ↓
Is it cached?
   ├── YES → return immediately
   │
   └── NO → ask origin

5. Invalidation

Delete cached content so CloudFront gets a fresh version.


S3:
V2

CloudFront:
V1

       ↓
Invalidation

CloudFront:
V2

18. The most important mental model

Remember this:


        CLOUD FRONT
        ┌────────────────────┐
User →  │ Cache / Edge Layer │
        └─────────┬──────────┘
                    |
                    | cache miss
                    v
                ORIGIN
        ┌────────────────────┐
        │ S3 / EC2 / ALB /   │
        │ API Gateway / etc. │
        └────────────────────┘

CloudFront does not replace your application server.

It sits in front of it.

Think of it like a smart delivery warehouse:


Origin = main warehouse

CloudFront = regional warehouses

User = customer

If the regional warehouse already has the product:


Customer → Regional warehouse

No need to go all the way to the main warehouse.

Your recommended hands-on learning path

Since you're already working with Node.js, React, AWS Lambda, S3 and MongoDB, I'd learn CloudFront in this order:


1. S3 static website
       ↓
2. CloudFront + S3
       ↓
3. Cache HIT / MISS
       ↓
4. Cache invalidation
       ↓
5. Custom domain + HTTPS
       ↓
6. CloudFront + API Gateway
       ↓
7. CloudFront + Lambda
       ↓
8. CloudFront cache policies
       ↓
9. CloudFront + your React/Node.js application

You do need some hands-on practice, but you don't need to learn every CloudFront setting. If you can build the S3 → CloudFront → browser example above and understand origin, edge, cache hit/miss, and invalidation, you've already learned the core concept.
