AWS Lambda and containers

Think of AWS Lambda and containers as two ways to run your application code.

🟣 Lambda = "Run my code when needed"

You give AWS a function, and AWS runs it when something happens.

Example:


User → API Gateway → Lambda → MongoDB

If a user calls your API:

  1. AWS starts/runs your Lambda.
  2. Your code processes the request.
  3. Lambda finishes.
  4. You stop paying for that execution.

Good for:

  • APIs
  • Small backend functions
  • Event processing
  • Scheduled jobs
  • Serverless applications

You don't manage the server.

🟢 Container = "Give me my own packaged application"

You package your application together with its environment.

For example:


Docker Container
├── Node.js
├── Your application
├── Dependencies
└── Configuration

Then you can run that container on services like ECS, EKS, or your own server.


User → Load Balancer → Container → MongoDB

The container typically stays running and waits for requests.

Good for:

  • Large applications
  • Long-running services
  • Applications needing specific environments
  • Microservices
  • WebSocket/real-time applications

The simplest difference

Lambda Container
Runs When needed Usually continuously
Server management AWS handles it You manage more of it
Scaling Automatic You configure/manage scaling
Startup Can have cold starts Usually already running
Long-running tasks ❌ Not ideal ✅ Good
Cost model Pay for execution Pay for running resources
Deployment Function Entire application environment
Example API endpoint Node.js backend server

Easy analogy

Lambda: 🍔

"Cook this burger when someone orders it."

Container: 🍳

"Keep a kitchen running and ready to cook burgers."

For your Node.js + API Gateway + MongoDB architecture, Lambda is excellent when your backend is mostly request/response APIs. Containers become more attractive when your backend needs to run continuously, maintain persistent connections, or perform long-running workloads.

The biggest difference becomes much clearer when you see the same Node.js API implemented both ways.

Lambda handler


// src/handlers/users.ts

import { APIGatewayProxyHandler } from "aws-lambda";
import { getUsers } from "../services/userService";

export const handler: APIGatewayProxyHandler = async () => {
  try {
    const users = await getUsers();

    return {
      statusCode: 200,
      body: JSON.stringify(users),
    };

  } catch (error) {
    return {
      statusCode: 500,
      body: JSON.stringify({
        message: "Internal server error",
      }),
    };
  }
};

Notice something important:

There is no Express server.

You don't do:


app.listen(3000);

AWS invokes your function.

Service


// src/services/userService.ts

import { getDatabase } from "../database/mongo";

export async function getUsers() {
  const db = await getDatabase();

  return db
    .collection("users")
    .find({})
    .toArray();
}

MongoDB connection


// src/database/mongo.ts

import { MongoClient } from "mongodb";

const client = new MongoClient(process.env.MONGO_URI!);

let db: any;

export async function getDatabase() {
  if (!db) {
    await client.connect();
    db = client.db("myapp");
  }

  return db;
}

The connection can potentially be reused across Lambda invocations.

Serverless configuration


service: my-api

provider:
  name: aws
  runtime: nodejs24.x

functions:

  getUsers:
    handler: src/handlers/users.handler
    events:
      - http:
          path: users
          method: get

getUsers()

MongoDB

You don't manage a server process.

import express from "express";

const app = express();

This is the major difference.

With containers:


app.listen(3000);

Routes


// src/routes/userRoutes.ts

import { Router } from "express";

const router = Router();

router.get("/", getUsers);

export default router;

Controller


// src/controllers/userController.ts

import { Request, Response } from "express";
import { getUsers as getUsersService } from "../services/userService";

export async function getUsers(
  req: Request,
  res: Response
) {
  try {
    const users = await getUsersService();

    res.json(users);

  } catch (error) {
    res.status(500).json({
      message: "Internal server error",
    });
  }
}

The service and MongoDB code can be almost identical.

             MongoDB

You don't manually create those servers.

You have containers:


            Load Balancer
                │

The key mental model

Think of it this way:

Lambda:


REQUEST
   ↓
RUN FUNCTION
   ↓
RESPONSE
   ↓
DONE

Container:


START APPLICATION
       ↓
  SERVER RUNNING
       ↓
REQUEST → PROCESS → RESPONSE
       ↓
REQUEST → PROCESS → RESPONSE
       ↓
REQUEST → PROCESS → RESPONSE
       ↓
   SERVER STAYS RUNNING

So when you are designing a backend, the fundamental question is:

"Do I want AWS to run individual pieces of my code when needed, or do I want to run my own application server inside a packaged environment?"

That's essentially Lambda vs containers.

The easiest way to understand it is to compare a traditional Node.js server with Node.js running as AWS Lambda functions.

3. The biggest code difference

Traditional Node.js


const app = express();

app.get("/contacts", async (req, res) => {

    const contacts = await getContacts();

    res.json(contacts);
});

app.listen(3000);

You own the server process.

Serverless


export const handler = async (event) => {

    const contacts = await getContacts();

    return {
        statusCode: 200,
        body: JSON.stringify(contacts)
    };
};

AWS owns the server execution environment.

4. You can still use Express with Lambda

This is an important point.

Serverless doesn't necessarily mean:

"You cannot use Express."

You can do something like:


import express from "express";
import serverless from "serverless-http";

const app = express();

app.get("/contacts", async (req, res) => {
    const contacts = await getContacts();
    res.json(contacts);
});

export const handler = serverless(app);

Now:


API Gateway
     ↓
Lambda
     ↓
Express
     ↓
Your routes

So you can migrate an existing Node.js application toward serverless without completely rewriting your business logic.
