JavaScript library

A JavaScript library is a collection of pre-written JavaScript code that helps developers perform common tasks more easily and quickly.

Instead of writing everything from scratch, you can use a library's functions and features in your project.

Example

Without a library:


document.getElementById("demo").style.color = "blue";

With a library like jQuery:


$("#demo").css("color", "blue");

The library provides simpler and more convenient methods.

Popular JavaScript Libraries

  • jQuery – Simplifies DOM manipulation and event handling.
  • React – Builds interactive user interfaces.
  • Lodash – Provides utility functions for working with arrays, objects, and strings.
  • D3.js – Creates data visualizations.
  • Chart.js – Builds charts and graphs.

Library vs Framework

Library Framework
You call the library when needed. The framework controls the application flow.
More flexibility. More structure and rules.

In Simple Words

A JavaScript library is like a toolbox containing ready-made tools (functions and methods) that help you write less code and build applications faster.

The key idea is who is in control.

  • With a library, you are in control.
  • With a framework, the framework is in control.

This concept is often called Inversion of Control (IoC).

Library: You call the code

Your application decides when to use the library.


import _ from "lodash";

const numbers = [3, 1, 2];

const sorted = _.sortBy(numbers);

console.log(sorted);

Here:

  1. Your code starts running.
  2. Your code decides to call sortBy().
  3. The library returns the result.
  4. Your code continues.

Flow:


Your App
   ↓
Library Function
   ↓
Your App

You are driving the program.

Framework: The framework calls your code

Take React as an example.

You write a component:


function App() {
    return <h1>Hello</h1>
}

Notice that you never call App() yourself.

Instead, React does something like this internally:


// React (simplified)
const html = App();
render(html);

React decides:

  • when to create the component
  • when to call it again
  • when to update the screen

So React is driving the application.

Flow:


React Framework
      ↓
 Calls your component
      ↓
Your code returns UI
      ↓
React updates the page

Another example: Express.js

In an Express server, you write:


app.get("/users", (req, res) => {
    res.send("Hello");
});

You never write:


handler(req, res);

Instead, Express waits for an HTTP request.

When someone visits /users, Express calls your function.


Browser Request
       ↓
Express receives request
       ↓
Express calls your callback
       ↓
Your code sends a response

Express controls the flow.

Another example: Next.js

With Next.js, you simply create a file:


app/page.tsx
            

export default function Home() {
    return <h1>Home Page</h1>
}

You never write:


Home();

Next.js decides:

  • when to render the page
  • whether to render it on the server or client
  • how to route requests
  • when to fetch data
  • when to cache content

Again, the framework controls the lifecycle, while you provide the page component.

Framework = Restaurant Kitchen

You don't decide every step of the cooking process. The kitchen has an established workflow:

  1. Customer orders.
  2. Kitchen receives the order.
  3. Chef prepares the food.
  4. Waiter serves it.

Your role is like the chef—you provide the cooking logic—but the restaurant's system controls when your work happens.


Restaurant System
       ↓
Calls the Chef
       ↓
Chef cooks
       ↓
Restaurant serves customer

Summary

  • Library: You call the library. Your application controls the execution flow.
  • Framework: The framework calls your code. It controls the application's lifecycle, routing, rendering, and execution, while you provide the pieces (components, pages, handlers) that it invokes when needed.
