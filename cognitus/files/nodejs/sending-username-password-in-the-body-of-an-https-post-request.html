Sending a username/email and password in the body of an HTTPS POST request

Yes, sending a username/email and password in the body of an HTTPS POST request is still the industry-standard way to perform an initial login, including in many banking and financial systems.

Your example:


const response = await fetch("https://api.example.com/login", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify({
        email: "user@example.com",
        password: "password123"
    })
});

const data = await response.json();

console.log(data.token);

is fundamentally correct if HTTPS/TLS is enforced.

Why this is secure

When using HTTPS:

  • The entire HTTP request body is encrypted.
  • The email and password cannot be read by someone sniffing network traffic.
  • TLS provides:
    • Encryption
    • Integrity checking
    • Server authentication

So sending credentials in the JSON body is preferred over:

❌ URL query parameters


POST /login?email=user@example.com&password=password123

because URLs can end up in:

  • browser history
  • server logs
  • proxy logs
  • monitoring tools

What financial institutions typically add

1. TLS 1.2 or TLS 1.3 only

Banks usually require:


HTTPS
TLS 1.2+

and disable older protocols.

2. Multi-factor authentication (MFA)

Password alone is rarely enough.

Common flow:


Email + Password
        ↓
OTP / Authenticator App
        ↓
Access Token

Examples:

  • SMS OTP
  • TOTP (Google Authenticator)
  • Push notification approval
  • Hardware token

3. Rate limiting

Prevent brute-force attacks.

Example:


5 failed attempts
↓
Account temporarily locked

4. Password hashing on server

The password should never be stored directly.

Use:


Argon2id  ← preferred
bcrypt
scrypt

Never:


MD5
SHA1
SHA256(password)

without a password hashing algorithm.

5. Short-lived access tokens

Instead of returning:


{
    token: "valid-for-30-days"
}

financial systems often use:


{
    accessToken: "...",   // 5–15 min
    refreshToken: "..."
}

6. Secure token storage

For React Native:

Prefer:


react-native-keychain

or secure OS storage:

  • iOS Keychain
  • Android Keystore

Avoid:


AsyncStorage

for financial-grade authentication tokens.

7. Device fingerprinting / risk analysis

Many banks additionally check:

  • Device ID
  • IP reputation
  • Location changes
  • Impossible travel detection
  • Jailbroken/rooted devices

What is NOT industry standard anymore

Sending credentials on every request:


fetch("/account", {
    headers: {
        email: "...",
        password: "..."
    }
});

Instead:


Authorization: Bearer <access_token>

after login.

Example:


fetch("/account", {
    headers: {
        Authorization: `Bearer ${accessToken}`
    }
});

For a React Native + Node.js financial application

A common architecture is:


React Native App
      ↓ HTTPS
POST /auth/login
      ↓
email + password
      ↓
Server validates password (Argon2)
      ↓
MFA challenge
      ↓
JWT Access Token (15 min)
Refresh Token (30 days)
      ↓
Store securely in Keychain/Keystore
      ↓
Authorization: Bearer

This is the pattern used by many modern fintech, banking, and enterprise systems. The critical requirement is that credentials are transmitted only over HTTPS and are backed by strong server-side controls such as MFA, rate limiting, secure password hashing, and secure token management.
