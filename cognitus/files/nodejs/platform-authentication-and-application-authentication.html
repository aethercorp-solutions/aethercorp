Platform authentication vs Application authentication

The simplest way to think about it is:

  • Platform authentication = “Which platform are you using?”
  • Application authentication = “Which user/application is allowed to use my backend?”

In your AWS + Node.js serverless architecture, you typically want both.

1. Platform authentication

This identifies where the request comes from or which platform-specific authentication mechanism is being used.

Examples:

  • iOS → Sign in with Apple / Google Sign-In
  • Android → Google Sign-In
  • Web → Google OAuth / web login
  • Internal service → API key or service credentials

For example:


iOS
  ↓
Apple / Google authentication
  ↓
identity from provider

Platform authentication answers:


"How did this user authenticate?"
"Which platform/provider is involved?"

You might have:


platform = "ios"
platform = "android"
platform = "web"

2. Application authentication

This is authentication between your client and your own backend.

For your system:


React Native / Web
       ↓
   Login
       ↓
Your Node.js API
       ↓
Application JWT

After successful login, your backend can issue something like:


{
    "accessToken": "your-application-jwt",
    "refreshToken": "...",
    "userId": "123",
    "platform": "ios"
}

The application JWT is then used on API requests:


Authorization: Bearer <application-jwt>

Your Lambda/API Gateway middleware verifies:


JWT signature
JWT expiration
user identity
claims

Application authentication answers:


"Is this request authenticated with MY application?"
"Which user is making this request?"
"Is their application session still valid?"

The important distinction

Imagine a user logs in with Google on iOS:


                PLATFORM AUTH
                iPhone ────────────────→ Google
                                           │
                                           │ Google identity/token
                                           ↓
                                    Your Node.js API
                                           │
                                           │ verify Google identity
                                           ↓
                              APPLICATION AUTH
                                    Your JWT
                                           │
                                           ↓
                                 Your API endpoints

Google's token is not necessarily your application's session token.

You can use Google's authentication to establish identity, then issue your own application JWT.

Why separate them?

This becomes especially important with your iOS + Android + Web architecture.

You could have:


                ┌── iOS ──────── Google / Apple
                │
User ────────────┼── Android ──── Google
                │
                └── Web ──────── Google
                        │
                        ↓
                 Identity Provider
                        │
                        ↓
                 Your Backend
                        │
                        ↓
               Application JWT
                        │
             ┌──────────┼──────────┐
             ↓          ↓          ↓
           iOS       Android      Web

The platform/provider authentication can vary, while your application's authentication remains consistent.

For example:

Layer iOS Android Web
Platform authentication Apple/Google Google Google
Provider token Apple/Google token Google token Google token
Backend authentication Your JWT Your JWT Your JWT
Refresh mechanism Your refresh token Your refresh token Your refresh token

In your current architecture

Based on the JWT/refresh-token system you've been working on, I'd recommend thinking of it as:


                PLATFORM AUTHENTICATION
                ───────────────────────
                Google / Apple / etc.
                         │
                         ↓
                Verify provider token
                         │
                         ↓
                Find/create application user
                         │
                         ↓
                APPLICATION AUTHENTICATION
                ─────────────────────────
                Application Access JWT
                         │
                         ↓
                API requests
                         │
                 JWT expires
                         ↓
                Application refresh
                         │
                         ↓
                New Application JWT

So when your application JWT expires, you generally do not make the user log in to Google/Apple again. Your refresh-token mechanism should establish a new application session.

That distinction is also why your earlier problem with userTokenMustExist rejecting an expired application JWT matters: the refresh endpoint needs a separate validation path that can accept an expired-but-authentic JWT and use the refresh credential to issue a new application JWT.

Firebase Authentication with Google and direct Google OAuth using Google's SDK use the same underlying Google OAuth identity system, but they have different responsibilities and flows.

1. Direct Google OAuth

Your app talks directly to Google:


iOS / Android / Web
       ↓
Google OAuth SDK
       ↓
Google
       ↓
Google ID Token / Access Token
       ↓
Your Node.js backend
       ↓
Verify Google token
       ↓
Create your own application session/JWT

You are responsible for:

  • Google OAuth configuration
  • verifying Google ID tokens
  • managing your application's users
  • issuing your own JWT/session
  • refresh-token handling
  • linking accounts
  • platform-specific OAuth behavior

For example, your existing architecture can do:


Google SDK
   ↓
Google ID Token
   ↓
POST /auth/google
   ↓
Node.js
   ↓
Verify Google token
   ↓
Find/create user
   ↓
Issue Application JWT

2. Firebase Authentication with Google

Firebase sits between your application and Google:


iOS / Android / Web
       ↓
Firebase Auth SDK
       ↓
Google
       ↓
Firebase Authentication
       ↓
Firebase ID Token
       ↓
Your Node.js backend
       ↓
Verify Firebase ID Token

Firebase handles much of the authentication infrastructure for you:

  • Google sign-in
  • user identity management
  • token issuance
  • token refresh
  • account linking
  • authentication state
  • multiple authentication providers

Your backend verifies the Firebase ID token, rather than directly verifying Google's ID token.

The important distinction

The Google account is ultimately the same identity, but the token your backend receives is different.

Direct Google OAuth Firebase Auth + Google
Identity provider Google Google through Firebase
SDK Google SDK Firebase Auth SDK
Backend verifies Google ID token Firebase ID token
User database You manage it Firebase manages auth users
Token management You manage more Firebase handles much of it
Google API access Straightforward Usually still need Google OAuth access token
Custom backend JWT You can issue one You can still issue one
Complexity More control Easier authentication

For your AWS Node.js architecture

Given the authentication system you've been building, you could have:


                ┌── Google OAuth
                iOS ─────────┤
                             │
                Android ─────┤──→ Node.js API ──→ MongoDB
                             │
                Web ─────────┘

with your backend issuing your own:


Application Access JWT
Application Refresh Token

Or:


                ┌── Google
                ↓
   iOS/Android/Web
                ↓
          Firebase Auth
                ↓
         Firebase ID Token
                ↓
          Node.js API
                ↓
             MongoDB
                ↓
      Your Application JWT

So Firebase Auth is not simply "another Google OAuth SDK." It is an authentication service that can use Google as an identity provider.

For your current multi-platform iOS + Android + Web + AWS Serverless architecture, the choice mainly comes down to whether you want Firebase to own the authentication layer or whether you want your Node.js backend to own authentication directly.
