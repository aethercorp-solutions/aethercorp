OAuth and Access Token for AI Agents

Think of OAuth as the process, and an access token as the key you get from that process.

Simple example: Login with Google

You have an app that wants to access your Google contacts.

1. OAuth = the authorization process

Your app says:

"Google, can this user allow me to access their contacts?"

The user logs into Google and clicks Allow.

That's OAuth.

2. Access token = the permission/key

After authorization, Google gives your app an access token:


access_token = "eyJhbGciOi..."

Your app then sends it when calling Google's API:


GET /contacts
Authorization: Bearer eyJhbGciOi...

Google checks the token and says:

"This token is valid and has permission to access contacts."

The difference

OAuth Access Token
Authorization protocol/process Credential/token
Handles how permission is granted Proves that permission
Involves login, consent, redirects, etc. Sent with API requests
Example: "Allow this app to access your contacts" Authorization: Bearer <token>

Easy analogy

Imagine entering a building:

OAuth = the process of getting permission from security.

Access token = the temporary badge security gives you.

You don't use "OAuth" to call the API. You use the access token.

Where refresh tokens fit

Usually the flow looks like:


User
  ↓
OAuth authorization
  ↓
Authorization Server
  ↓
Access Token + Refresh Token
  ↓
Your App
  ↓
API request using Access Token

Access token: short-lived → used to access APIs.

Refresh token: longer-lived → used to get a new access token when the old one expires.

So in your Swift/API work, when you see:


Authorization: Bearer \(accessToken)

you're looking at the result of an OAuth authorization flow, not OAuth itself.

The same OAuth + access token concept is very important when building AI agents and MCP servers.

Think of an AI agent as a user-controlled application that needs permission to use external services.

1. The basic architecture


User
 ↓
AI Agent / LLM
 ↓
MCP Client
 ↓
MCP Server
 ↓
OAuth
 ↓
Access Token
 ↓
External API

For example, imagine you build an AI agent that can manage a user's Google Contacts.

The user asks:

"Find John in my contacts."

The LLM decides it needs a tool:


LLM
 ↓
search_contacts()
 ↓
MCP Server
 ↓
Google People API

But the MCP server needs permission to access Google's API.

That's where OAuth comes in.

2. OAuth handles authorization

The first time the user connects Google:


AI Agent
   ↓
"Connect Google"
   ↓
Google OAuth
   ↓
User clicks "Allow"
   ↓
Access Token
   ↓
Your application

Your application might receive:


{
    "access_token": "abc123...",
    "refresh_token": "xyz789..."
}

The important thing is that the LLM itself should generally not be responsible for storing or managing these credentials.

Your application/MCP infrastructure handles them.

3. MCP uses the authenticated identity

Your MCP server might expose:


search_contacts
get_contact
create_contact
update_contact

The LLM sees something like:


Tool: search_contacts

Input:
{
  "name": "John"
}

The MCP server receives the request and uses the user's authenticated access token:


MCP Server
    ↓
Access Token
    ↓
Google People API
    ↓
Contacts

Then it returns the result to the LLM:


{
    "name": "John Smith",
    "email": "john@example.com"
}

The LLM can then respond:

"I found John Smith. His email is john@example.com."

4. Where the LLM fits

The LLM is primarily the reasoning layer.

For example:


                User:
"Find John and send him an email saying I'll call tomorrow."

              ↓

             LLM
              ↓
       ┌──────┴──────┐
       ↓             ↓
search_contacts    send_email
       ↓             ↓
    MCP tool       MCP tool
       ↓             ↓
   Google API    Gmail API

The LLM decides:

"I need to search contacts first."

Then:

"I found John. Now I need to send an email."

The LLM doesn't need to know Google's API implementation details.

5. OAuth protects each user's data

This becomes especially important if you have a SaaS AI agent.

Suppose you have:


Paul → AI Agent → MCP → Google
John → AI Agent → MCP → Google
Mary → AI Agent → MCP → Google

Each user has their own OAuth authorization:


Paul → Paul Access Token
John → John Access Token
Mary → Mary Access Token

So when Paul asks:

"Show me my contacts."

Your backend must use Paul's token, not somebody else's.

6. A practical architecture for your stack

Given a modern full-stack setup, you could build:


                ┌───────────────┐
                │     User      │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │ React /       │
                │ React Native  │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │ AI Agent      │
                │ LLM           │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │ MCP Client    │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │ MCP Server    │
                └───────┬───────┘
                        ↓
               ┌─────────────────┐
               │ OAuth / Token   │
               │ Management      │
               └────────┬────────┘
                        ↓
             ┌─────────────────────┐
             │ Google / Gmail /    │
             │ Calendar / CRM API  │
             └─────────────────────┘

Your backend could store token metadata in MongoDB:


User
 ├── userId
 ├── email
 └── integrations
      └── google
           ├── accessToken
           ├── refreshToken
           └── expiresAt

Although in production, don't store raw access/refresh tokens casually in MongoDB. Encrypt sensitive tokens and restrict access to them.

7. The key idea

Remember these four roles:


OAuth
  ↓
Gets permission

Access Token
  ↓
Proves permission

MCP
  ↓
Provides standardized tools

LLM
  ↓
Decides which tools to use

So an AI agent doesn't replace OAuth.

Instead:

OAuth gives the agent authorized access → MCP exposes that access as tools → LLM decides when to use those tools.

That's the foundation of many modern AI agent + MCP + SaaS integrations.
