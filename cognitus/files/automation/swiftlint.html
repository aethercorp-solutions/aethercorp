SwiftLint

SwiftLint is a static analysis tool for Swift that helps you write cleaner, more consistent, and less error-prone code. It analyzes your Swift source files and reports violations of coding style and best practices, similar to how ESLint works for JavaScript.

What SwiftLint does

For example, it can detect:

  • Variables that should be constants (let instead of var)
  • Lines that are too long
  • Force unwrapping (!)
  • Force casting (as!)
  • Trailing whitespace
  • Unused imports
  • Missing documentation comments (if configured)
  • Functions or types that are too large
  • Naming convention violations

Example:


// ❌ SwiftLint warning
var name = "Paul"

// ✅ Preferred
let name = "Paul"

Another example:


// ❌ Force unwrap
let image = UIImage(named: "logo")!

// ✅ Safer
guard let image = UIImage(named: "logo") else {
    return
}

Why use SwiftLint?

Benefits include:

  • Consistent coding style across the team
  • Catches common mistakes before runtime
  • Makes code reviews easier
  • Makes code reviews easier
  • Integrates with Xcode and CI/CD pipelines

This is especially useful if you're working in a team or maintaining a large iOS project.

How to install

Using Homebrew


brew install swiftlint

Or add it as a Swift Package plugin in Xcode for newer projects. SwiftLint supports both approaches.

Running SwiftLint

From your project directory:


swiftlint

To automatically fix some issues:


swiftlint --fix

Configuration

Create a file named:


.swiftlint.yml

Example:


disabled_rules:
  - trailing_whitespace

opt_in_rules:
  - force_unwrapping
  - empty_count

line_length: 120

identifier_name:
  min_length: 2

This lets you enable, disable, or customize rules for your project.

Integrating with Xcode

Add a Run Script Build Phase:


if command -v swiftlint >/dev/null; then
    swiftlint
else
    echo "warning: SwiftLint not installed"
fi

Now every build will automatically check your code and show warnings in Xcode.

SwiftLint vs ESLint

SwiftLint ESLint
Swift JavaScript / TypeScript
Checks Swift style and best practices Checks JS/TS style and best practices
.swiftlint.yml eslint.config.js / .eslintrc
Runs during Xcode builds or CI Runs during npm scripts or CI

Since you've been working on iOS projects and setting up CI/CD with Bitbucket, SwiftLint is commonly added to the pipeline so that every pull request is checked automatically. A typical pipeline looks like:

  1. Build the app.
  2. Run unit tests.
  3. Run SwiftLint.
  4. If linting fails, fail the build.
  5. Upload to TestFlight if all checks pass.

This helps enforce coding standards before code is merged.
