macOS Runner

A macOS Runner is a macOS machine (physical or virtual) that executes automated tasks in a CI/CD pipeline. It's commonly used to build, test, sign, and deploy Apple applications such as iOS, macOS, watchOS, and tvOS apps.

Because Apple's build tools (Xcode, Simulator, code signing) only run on macOS, you need a macOS runner whenever your pipeline builds Apple apps.

How it works

When you push code to your repository:


Developer
    │
    ▼
Git Repository (GitHub/Bitbucket/GitLab)
    │
    ▼
CI/CD Pipeline
    │
    ▼
macOS Runner
    ├── Checks out code
    ├── Installs dependencies
    ├── Runs tests
    ├── Builds app
    ├── Signs app
    ├── Uploads to TestFlight/App Store
    └── Reports success/failure

What does a macOS runner do?

A typical iOS pipeline might execute commands like:


xcodebuild clean
xcodebuild test
xcodebuild archive
xcodebuild -exportArchive

Or with Fastlane:


bundle exec fastlane beta

The runner performs these commands automatically.

Why macOS?

Apple requires Xcode to build Apple apps.

Only macOS supports:

  • Xcode
  • iOS Simulator
  • Code Signing
  • Notarization
  • App Store Connect uploads

Linux and Windows runners cannot build native iOS/macOS apps.

Types of macOS runners

1. Hosted macOS Runner (Cloud)

Provided by CI/CD platforms.

Examples:

  • GitHub Actions
  • Bitbucket Pipelines
  • Azure DevOps
  • CircleCI

Example:


runs-on: macos-latest

GitHub automatically starts a temporary macOS VM, runs your workflow, and then discards it.

Pros

  • No maintenance
  • Always up to date
  • Easy to set up

Cons

  • Usage limits or higher cost
  • Build time limits
  • Less control over the environment

2. Self-hosted macOS Runner

A Mac you own (Mac mini, Mac Studio, MacBook, etc.) runs jobs from your CI/CD platform.

Example:


Mac mini in your office
        ▲
        │
GitHub Runner Service
        ▲
        │
GitHub Actions

Pros

  • Full control
  • Can install custom tools
  • No per-minute hosted build charges
  • Faster if dedicated

Cons

  • You maintain the machine
  • Must keep Xcode updated
  • Hardware failures are your responsibility

Example in Bitbucket Pipelines

A pipeline can target a macOS runner:


pipelines:
  default:
    - step:
        runs-on:
          - self.hosted
          - macos
        script:
          - xcodebuild -version
          - bundle install
          - bundle exec fastlane beta

Here, Bitbucket sends the build to a registered macOS runner.

Typical tools installed on a macOS runner

  • Xcode
  • Command Line Tools
  • Ruby
  • Fastlane
  • CocoaPods
  • Swift Package Manager
  • Homebrew
  • Git
  • Node.js (if needed)
  • Java (for Android builds, if applicable)

Common use cases

For iOS apps, a macOS runner is often used to:

  • Build the app
  • Run unit tests
  • Run UI tests
  • Create an .ipa
  • Sign the app
  • Upload to TestFlight
  • Upload to the App Store
  • Automatically update TestFlight release notes using the App Store Connect API

In your workflow

Since you've been working on Bitbucket CI/CD and automating TestFlight uploads and release notes, a macOS runner is the machine that executes steps such as:


bundle exec fastlane beta

or


xcodebuild archive

followed by uploading the build to App Store Connect and, if desired, updating the TestFlight metadata via the App Store Connect API.

Without a macOS runner, the iOS-specific parts of your CI/CD pipeline (building, signing, and uploading the app) cannot be performed.
