CI/CD

The easiest way to understand CI/CD is to think of it as an automatic factory for your app.

Before CI/CD:


Write code
    ↓
Build manually
    ↓
Run tests manually
    ↓
Upload manually
    ↓
Hope nothing breaks 😅

With CI/CD:


Write code
    ↓
Push to Git/Bitbucket
    ↓
🤖 CI/CD does everything automatically

What does CI/CD mean?

  • CI = Continuous Integration
    • Automatically checks that your code builds and passes tests whenever you push code.
  • CD = Continuous Delivery / Continuous Deployment
    • Automatically prepares or deploys your app after CI succeeds.

Simple Example

Imagine you're building an iPhone app.

Normally you do this:


1. Open Xcode
2. Build
3. Run tests
4. Archive
5. Upload to TestFlight
6. Wait
7. Tell testers

Every single release.

With CI/CD:

You only do:


git push origin main

Everything else happens automatically.

That's CI/CD.

What is a Runner?

A Runner is simply a computer that executes the pipeline.

For iOS:


Bitbucket
     │
     ▼
macOS Runner
     │
     ├── xcodebuild
     ├── swiftlint
     ├── fastlane
     └── App Store Connect

Since Xcode only runs on macOS, iOS projects require a macOS runner.

Example Bitbucket Pipeline

Create:


bitbucket-pipelines.yml

Example:


pipelines:
  branches:
    main:
      - step:
          name: Build iOS
          runs-on:
            - self.hosted
            - macos
          script:
            - bundle install
            - pod install
            - swiftlint
            - xcodebuild test
            - xcodebuild archive
            - fastlane beta

When you push:


git push origin main

Bitbucket automatically starts the runner.

What Fastlane Does

Fastlane automates Xcode tasks.

Instead of:


Open Xcode

Product
↓

Archive

↓

Upload

You simply run:


fastlane beta

Example lane:


lane :beta do
  build_app
  upload_to_testflight
end

Why Companies Use CI/CD

Without CI/CD:

  • Developers build manually.
  • People forget steps.
  • Releases take longer.
  • More deployment mistakes happen.

With CI/CD:

  • Every build follows the same process.
  • Problems are caught earlier with automated builds and tests.
  • Releases become faster and more reliable because repetitive tasks are automated.
