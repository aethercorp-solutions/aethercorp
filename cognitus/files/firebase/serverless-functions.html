Serverless Functions

The easiest way to understand them is:

Firebase Functions = Google Cloud Functions designed around Firebase.

Google Cloud Functions = Google's general-purpose serverless functions.

AWS Lambda = Amazon's equivalent serverless function service.

Side-by-side

Feature Firebase Functions Google Cloud Functions AWS Lambda
Cloud provider Google Google AWS
Main purpose Firebase applications General backend/serverless General backend/serverless
Service Firebase Functions Cloud Functions Lambda
Triggered by Firebase + Google events + HTTP HTTP + Google Cloud events AWS events + HTTP/API Gateway
Best with Firebase Google Cloud AWS
Database integration Firestore, Realtime DB Any Google Cloud DB/service DynamoDB, RDS, etc.

1. Firebase Functions

Firebase Functions are essentially a Firebase-oriented serverless backend.

For example:


React Native App
       ↓
Firebase Auth
       ↓
Firebase Function
       ↓
MongoDB / Firestore / external API

You can write:


exports.createUser = functions.https.onCall(async (data, context) => {
    // backend logic
});

Firebase can also trigger functions when things happen in Firebase:


User signs up
     ↓
Firebase Auth
     ↓
Function executes
     ↓
Create user profile
     ↓
Send notification

They're particularly convenient for mobile applications.

2. Google Cloud Functions

Google Cloud Functions are Google's general serverless compute platform.

Think:


HTTP request
     ↓
Cloud Function
     ↓
Business logic
     ↓
Cloud SQL / BigQuery / Storage / API

You don't have to use Firebase.

For example, you could have:


React Web App
       ↓
Cloud Function
       ↓
PostgreSQL

or:


Cloud Storage
     ↓
Cloud Function
     ↓
Process uploaded image

Firebase Functions actually uses Google's underlying cloud infrastructure.

3. AWS Lambda

Amazon Web Services Lambda is Amazon's equivalent concept.

For example:


React Native
     ↓
API Gateway
     ↓
AWS Lambda
     ↓
MongoDB

Or:


S3 upload
   ↓
Lambda
   ↓
Process image

AWS Lambda is deeply integrated with the AWS ecosystem:


Lambda
 ├── API Gateway
 ├── S3
 ├── DynamoDB
 ├── SQS
 ├── SNS
 ├── EventBridge
 ├── Cognito
 └── CloudWatch

The important distinction

Don't think:


Firebase Function
Google Function
AWS Function

as three completely different programming concepts.

Think:


                SERVERLESS FUNCTIONS

                ┌─────────────────────┐
                │   Your code         │
                │   Node/Python/etc.  │
                └──────────┬──────────┘
                           │
             ┌─────────────┴─────────────┐
             ↓                           ↓
        Google Cloud                  AWS
             │                           │
      ┌──────┴──────┐                 Lambda
      ↓             ↓
   Firebase       Cloud
   Functions     Functions

The biggest difference is the surrounding ecosystem and how you trigger/connect the function.

In your Castanet architecture

Based on the architecture you've been working with, you actually have something close to:


React / React Native
        │
        ↓
Firebase Auth
        │
        ↓
AWS Lambda / API Gateway
        │
        ├── MongoDB
        ├── Google People API
        └── other services

That is perfectly valid.

You don't need Firebase Functions just because you're using Firebase Auth.

For example:


Firebase Authentication
        ↓
JWT
        ↓
AWS API Gateway
        ↓
AWS Lambda
        ↓
MongoDB

Firebase handles identity, while AWS handles backend computation.

That's actually a useful architecture for Castanet because you can use Firebase for mobile-oriented services while keeping your main API/backend in AWS.

Simple rule

Use Firebase Functions when:

  • Your application is heavily Firebase-based.
  • You want easy Firebase event triggers.
  • You want quick mobile/backend development.

Use Google Cloud Functions when:

  • You're primarily using Google Cloud.
  • You need serverless processing independent of Firebase.
  • You're integrating services such as Cloud Storage, Pub/Sub, BigQuery, etc.

Use AWS Lambda when:

  • Your backend is primarily AWS.
  • You're using API Gateway, S3, SQS, DynamoDB, EventBridge, etc.
  • You need a larger AWS serverless architecture.

One important modern detail

The terminology can be confusing because Google has evolved its serverless offerings. Cloud Functions is now closely tied to Cloud Run infrastructure in Google's newer 2nd-generation model. So when learning modern Google serverless architecture, you should also understand Cloud Run, not just Cloud Functions.

If you're aiming toward Systems Architect, I'd learn the three concepts as:

Firebase Functions → Google Cloud Functions/Cloud Run → AWS Lambda

and, more importantly, learn when to choose each architecture, rather than memorizing the APIs.
