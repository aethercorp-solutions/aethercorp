React Native and Flutter

React Native and Flutter both let you build iOS and Android apps from one codebase, but their architectures are fundamentally different.

The simplest technical distinction is:

React Native = JavaScript/TypeScript code controlling native platform components through a native runtime/bridge architecture.

Flutter = Dart code rendered by Flutter's own rendering engine, largely independent of native UI widgets.

Since you work with native iOS (Swift/Objective-C/UIKit) as well as React Native, this architectural difference is especially important.

1. High-level architecture

React Native


        JavaScript / TypeScript
                │
                ▼
       React component tree
                │
                ▼
      React Native runtime
                │
       ┌────────┴────────┐
       │                 │
       ▼                 ▼
  Native Modules    Native Components
       │                 │
       ▼                 ▼
    Obj-C/Swift       UIKit / Android

Your code:


<View>
    <Text>Hello</Text>
    <Button title="Login" />
</View>

doesn't mean React Native draws those pixels itself.

Instead, React Native ultimately causes native platform views/components to be created or updated.

On iOS, this historically means things such as:


RCTView
RCTText
UIButton / custom native components
UIView
UIViewController

and corresponding Objective-C/Swift implementations.

2. Flutter architecture

Flutter is quite different.


                Dart
                │
                ▼
         Flutter Framework
                │
                ▼
         Flutter Engine
                │
         ┌──────┴──────┐
         │             │
      Skia/Impeller   Dart VM
         │
         ▼
      GPU rendering
         │
         ▼
        Pixels

Flutter generally does not ask UIKit:

"Please create a UIButton."

Instead, Flutter's rendering system draws the button itself.

Conceptually:


Flutter Widget
      ↓
Element
      ↓
RenderObject
      ↓
Flutter Engine
      ↓
GPU
      ↓
Pixels

So a Flutter button is primarily a Flutter-rendered object rather than a native UIButton.

3. The biggest architectural difference

This is probably the most important thing to understand.

React Native

React Native is essentially:


React
  ↓
Native UI

Flutter is:


Flutter
  ↓
Flutter-rendered UI

For example:

React Native


<View style={styles.container}>
    <Text>Hello</Text>
</View>

The React Native framework maps this into native/platform-backed UI structures.

Flutter


Container(
  child: Text('Hello'),
)

Flutter's rendering engine handles the rendering.

It doesn't need to translate that Text into a native UILabel for normal Flutter UI.

4. React Native's JavaScript runtime

React Native applications contain JavaScript/TypeScript.

For example:


const Contact = ({name}: Props) => {
    return (
        <View>
            <Text>{name}</Text>
        </View>
    );
};

The JavaScript executes inside a JavaScript runtime.

Modern React Native uses Hermes heavily.

Conceptually:


TypeScript
    ↓
JavaScript
    ↓
Hermes
    ↓
React Native runtime
    ↓
Native platform

Your TypeScript isn't directly compiled into ARM machine code in the same manner as a native Swift application.

5. Flutter's Dart runtime

Flutter uses Dart.


class Contact extends StatelessWidget {
    final String name;
    
    const Contact({
        required this.name,
    });
    
    @override
    Widget build(BuildContext context) {
        return Column(
        children: [
            Text(name),
        ],
        );
    }
}

Dart has multiple execution modes.

Development

Dart VM provides things such as:


Hot Reload
Debugging
Runtime inspection

Release

Dart can be compiled ahead-of-time into native machine code.

Conceptually:


Dart
 ↓
AOT compiler
 ↓
ARM64 machine code
 ↓
iOS / Android

This is one reason Flutter release applications don't require a JavaScript runtime to execute the application logic.

6. React Native's rendering model

React Native uses React's reconciliation model.

Suppose you have:


<Text>{count}</Text>

and:


setCount(count + 1);

React determines what changed.

Conceptually:


State change
     ↓
React render
     ↓
Reconciliation
     ↓
Determine changed UI
     ↓
Update native representation

This is similar to React on the web conceptually, but the target isn't the DOM.

Instead of:


React → DOM

you have:


React → React Native host components

7. Flutter's widget tree

Flutter uses a different model.

You write:


Column(
  children: [
    Text('Paul'),
    Text('Developer'),
  ],
)

Flutter has several layers.

Widget

Describes configuration.


Widget

Element

Represents the widget's position/lifecycle in the tree.


Widget
  ↓
Element

RenderObject

Handles layout and painting.


Element
  ↓
RenderObject

Then:


RenderObject
      ↓
Flutter Engine
      ↓
GPU

This is a major conceptual difference from React Native.

8. React Native has native UI constraints

Suppose you're building a complicated iOS interface.

React Native might ultimately interact with:


UIView
UIViewController
UIScrollView
UITextField
UIImageView
UINavigationController

This is advantageous when you need deep integration with the operating system.

For example:


React Native
     ↓
Native Module
     ↓
Swift / Objective-C
     ↓
UIKit
     ↓
iOS

You can create:


RCT_EXPORT_MODULE(MyScanner);

or modern native module implementations.

This lets React Native access capabilities that JavaScript itself cannot directly access.

9. Flutter also has platform channels

Flutter has a similar concept, but the mechanism is different.

Flutter code:


MethodChannel('scanner')
    .invokeMethod('startScanner');

can communicate with:


Dart
 ↓
Platform Channel
 ↓
Swift / Objective-C

or:


Dart
 ↓
Platform Channel
 ↓
Kotlin / Java

So:


React Native:

JS
 ↓
Native Module
 ↓
Swift / Obj-C


Flutter:

Dart
 ↓
Platform Channel
 ↓
Swift / Obj-C

Both can access native functionality.

10. Native modules vs Flutter plugins

The concepts are similar.

React Native

You might create:

MyScannerModule.swift

and expose:


startScanner()
stopScanner()

to JavaScript.

Flutter

You might create:

scanner_plugin

with:


Dart API
   ↓
Platform implementation
   ↓
Swift / Kotlin

Flutter's ecosystem calls these plugins.

11. UI rendering is where Flutter becomes particularly different

Consider:


Button

React Native

Conceptually:


JS Button
   ↓
RN abstraction
   ↓
Native platform
   ↓
UIKit / Android View

Flutter


Dart Button
   ↓
Flutter Widget
   ↓
RenderObject
   ↓

   ↓

Flutter has much greater control over the rendering pipeline.

This is particularly useful for:

  • custom animations
  • highly customized UI

  • graphics

12. Why Flutter can look almost identical on iOS and Android

Because Flutter controls much of the rendering.

For example:


            Flutter UI
                │
       ┌────────┴────────┐
       ▼                 ▼
      iOS              Android
       │                 │
  Flutter Engine    Flutter Engine
       │                 │
       ▼                 ▼
      GPU               GPU

The same Flutter rendering system produces the interface.

Therefore:


iOS appearance
≈
Android appearance

unless you deliberately use platform-specific widgets/design.

13. React Native naturally follows platform conventions

React Native can take advantage of the platform's native behavior.

For example:


iOS
 ↓
UIKit behavior

Android
 ↓
Android framework behavior

That can be an advantage when you want the application to feel like a conventional native application.

14. Performance differences

This subject is often oversimplified.

It isn't accurate to say:

Flutter is fast, React Native is slow.

Modern React Native is significantly different from the old architecture.

A more useful comparison is:

Area React Native Flutter
Application language JS/TS Dart
Runtime Hermes/JS runtime Dart VM/AOT
UI Native/platform-backed abstractions Flutter-rendered
Rendering RN/native rendering architecture Flutter engine
Native integration Native Modules Plugins/platform channels
Hot reload Yes Yes
Release compilation JS + native runtime AOT native code
Custom rendering More involved Very strong
Native UI integration Very strong Possible, but indirect
Web ecosystem Very strong Separate Flutter ecosystem

15. React Native's New Architecture

This is particularly important for you because you're working with React Native 0.68.x.

Older React Native architecture:


JavaScript
    ↓
Bridge
    ↓
Native

The traditional architecture relied heavily on an asynchronous bridge.

Conceptually:


JS Thread
   │
   │ serialized messages
   ▼
Bridge
   │
   ▼
Native Modules / UI

This introduced overhead for certain communication patterns.

16. Modern React Native

Modern React Native introduced the New Architecture, centered around:


Fabric
TurboModules
JSI
Codegen

The conceptual architecture becomes closer to:


JavaScript / TypeScript
          │
          ▼
         JSI
          │
    ┌─────┴─────┐
    ▼           ▼
 Fabric     TurboModules
    │           │
    ▼           ▼
 Native UI    Native APIs

JSI

JavaScript Interface allows JavaScript and C++/native code to interact more directly.

Instead of everything being serialized through the old bridge model:


JS
 ↓
JSON-like serialization
 ↓
Bridge
 ↓
Native

modern React Native can do much more direct interop.

17. Fabric

Fabric is React Native's modern rendering architecture.

Conceptually:


React
 ↓
Shadow Tree
 ↓
Fabric
 ↓
Native UI

Fabric improves things such as:

  • rendering synchronization
  • concurrent rendering
  • native interoperability
  • performance
  • layout processing
  • integration with modern React

18. TurboModules

Old architecture:


JS
 ↓
Bridge
 ↓
Native Module

TurboModules:


JS
 ↓
JSI
 ↓
TurboModule
 ↓
Native

This can substantially reduce communication overhead.

25. React vs Flutter programming model

React Native:


function Contact({contact}) {
    return (
        <View>
        <Text>{contact.name}</Text>
        </View>
    );
}

The fundamental idea is:


state
 ↓
render
 ↓
UI

Flutter:


class Contact extends StatelessWidget {
    final ContactModel contact;
    
    const Contact({
        super.key,
        required this.contact,
    });
    
    @override
    Widget build(BuildContext context) {
        return Column(
        children: [
            Text(contact.name),
        ],
        );
    }
}

Flutter's fundamental abstraction is the:

Widget

Almost everything is a widget.

27. Native UI vs custom UI

This is an important decision point.

Suppose you want:


100% custom graphical interface

Flutter's model is naturally suited to that:


Widget
 ↓
RenderObject
 ↓
Engine
 ↓
GPU

React Native:


React component
 ↓
RN
 ↓

You can absolutely create custom components in React Native, but you're working within a different architecture.

28. Animations

Flutter has a very extensive animation system.

For example:


AnimationController
Tween
CurvedAnimation
AnimatedBuilder

Because Flutter controls the rendering pipeline, it can coordinate animations tightly with its frame rendering.

React Native has:


Animated
LayoutAnimation
Reanimated

The popular react-native-reanimated library moves substantial animation work away from the normal JS execution path.

Conceptually:


JS
 ↓
Animation definition
 ↓
UI-thread/native execution
 ↓
60/120 FPS

This is why modern React Native animation performance can be very good when implemented correctly.

29. Threading

A simplified React Native architecture can involve:


JavaScript thread
        │
        ├── React
        └── application logic

Native/UI thread
        │
        └── UI rendering

Other native threads
        │
        └── networking / background operations

Modern React Native complicates this architecture somewhat because JSI, Fabric, worklets, and native components can execute outside the traditional JS path.

Flutter typically has:


Dart UI thread
      │
      ▼
Flutter framework
      │
      ▼
Rendering

plus engine/platform threads.

Flutter's threading model is therefore different rather than simply "single-threaded."

30. Memory

React Native application memory includes things such as:


iOS process
 ├── JS runtime
 ├── React Native runtime
 ├── native UI
 ├── native modules
 └── application data

Flutter includes:


iOS process
 ├── Dart runtime
 ├── Flutter engine
 ├── widget/rendering structures
 ├── GPU resources
 └── application data

Flutter's engine adds a relatively substantial runtime footprint because the rendering engine is packaged with the application.

React Native leverages more of the platform UI infrastructure.

31. App size

Neither framework has a universally smaller application.

It depends heavily on:


framework version
dependencies
architecture
native libraries
assets
debug/release configuration

Flutter has to package its engine.

React Native packages its JS/runtime and native dependencies.

So don't use:

"Flutter is always smaller."

or:

"React Native is always smaller."

as a general rule.

34. A very important distinction: "cross-platform"

People often say:

"Both are cross-platform."

True, but they achieve it differently.

React Native


            Shared
                │
         React/TypeScript
                │
       ┌────────┴────────┐
       ▼                 ▼
     iOS               Android
       │                 │
    UIKit             Android UI

Flutter


            Shared
                │
               Dart
                │
          Flutter Engine
                │
       ┌────────┴────────┐
       ▼                 ▼
     iOS               Android

React Native shares application logic + UI abstraction, while relying much more on platform-native UI infrastructure.

Flutter shares application logic + rendering framework, with its own rendering engine.

Bottom line

The most fundamental difference isn't JavaScript vs Dart.

It's:

React Native's fundamental model:


React → native platform UI

Flutter's fundamental model:


Dart → Flutter rendering engine → pixels

And that leads to the practical differences in UI behavior, native integration, rendering, performance characteristics, architecture, debugging, dependency management, and how much platform-specific code you need.

For someone with your React + React Native + Swift/Objective-C/UIKit background, understanding JSI/Fabric/TurboModules and the native iOS embedding/lifecycle is particularly important because modern React Native is considerably different from the old "JavaScript bridge" architecture.
