Row Level Security (RLS)

Row Level Security (RLS) in Supabase is a PostgreSQL security feature that controls which rows (records) a user can read, insert, update, or delete.

Think of it as authorization at the database level instead of your API.

Without RLS:

  • Any authenticated user could potentially access all rows (depending on your API configuration).

With RLS:

  • Users can only access the rows your policies allow.

Simple Example

Imagine you have a todos table.

id title user_id
1 Buy milk user_1
2 Study Supabase user_2
3 Go gym user_1

If Alice logs in (user_1), she should only see:

id title
1 Buy milk
1 Go gym

She should never see:


Study Supabase

RLS makes this happen automatically.

Without RLS


const { data } = await supabase
    .from('todos')
    .select('*');

Result:


Buy milk
Study Supabase
Go gym

Everyone sees everything.

With RLS

Enable it:


ALTER TABLE todos ENABLE ROW LEVEL SECURITY;

Now nobody can access anything until you add policies.

If you run:


const { data } = await supabase
    .from('todos')
    .select('*');

Result:


[]

No rows.

Policy Example

Suppose every row has


user_id

that stores the owner's ID.

Create this policy:


CREATE POLICY "Users can view own todos"

ON todos

FOR SELECT

USING (
    auth.uid() = user_id
);

Now when a user queries


supabase
    .from("todos")
    .select("*");

Supabase automatically converts it conceptually into:


SELECT *

FROM todos

WHERE user_id = auth.uid();

You don't have to write the WHERE clause yourself.

Insert Policy

Allow users to insert only their own rows.


CREATE POLICY "Users can insert own todos"

ON todos

FOR INSERT

WITH CHECK (
    auth.uid() = user_id
);

Now this works:


await supabase
.from("todos")
.insert({
    title: "Learn RLS",
    user_id: user.id
});

But this is rejected:


await supabase
.from("todos")
.insert({
    title: "Hack",
    user_id: "someone_else"
});

Update Policy


CREATE POLICY "Users update own todos"

ON todos

FOR UPDATE

USING (
    auth.uid() = user_id
);

Only the owner can update.

Delete Policy


CREATE POLICY "Users delete own todos"

ON todos

FOR DELETE

USING (
    auth.uid() = user_id
);

auth.uid()

This is the most commonly used function.


auth.uid()

Example:


Logged in user

UUID

9a7b4b53-xxxx-xxxx

Table

id title user_id
1 Buy Milk 9a7b4b53...
2 Study 22222222...

Policy


auth.uid() = user_id

Only row 1 is visible.

auth.role()

You can also check the user's role.


auth.role() = 'authenticated'

or


auth.role() = 'anon'

Example:


USING (
    auth.role() = 'authenticated'
)

Only logged-in users can read.

Public Read Example

Suppose a posts table has:


title

content

published

Anyone can read published posts.


CREATE POLICY "Public posts"

ON posts

FOR SELECT

USING (
    published = true
);

Admin Example

Suppose you store:


profiles

id

role

A policy can allow admins to read everything:


USING (

EXISTS (

SELECT 1

FROM profiles

WHERE id = auth.uid()

AND role = 'admin'

)

)

Real Project Example

Imagine you're building a note-taking app.

Table:


notes

id

title

content

user_id

Policies:

Read:


USING (
    auth.uid() = user_id
)

Insert:


WITH CHECK (
    auth.uid() = user_id
)

Update:


USING (
    auth.uid() = user_id
)

Delete:


USING (
    auth.uid() = user_id
)

Now your frontend can simply do:


const { data } = await supabase
    .from("notes")
    .select("*");

No need for:


.where("user_id", user.id)

Even if someone modifies your frontend or calls the API directly, the database will still enforce access control.
