How OpenAI requests and executes a tool

OpenAI models can request tools such as APIs, database queries, web searches, or custom functions by generating a structured tool call. The model does not necessarily execute the code itself. Instead, the application or orchestration runtime receives the request, validates it, executes the corresponding function, and sends the result back to the model.

This is the foundation of tool calling, which enables AI applications to interact with external systems.

1. The architecture 


1. User
"Find customer 123 in the database."
            

2. OpenAI model
Interprets the request and decides whether a tool is needed.
            

3. Tool call
Structured function name and arguments, such as get_customer(id="123").
            

4. Application runtime
Validates arguments, checks permissions, and dispatches the function.
            

5. External system
Executes SQL, calls an API, or performs another operation.
            

6. Tool result -> Model
The result is added to the conversation so the model can interpret it and respond.

The important distinction is that the model chooses and describes the action, while the host application normally executes it.

2. Step 1 — Define a tool using a schema

Suppose you're building a Node.js backend and want the model to retrieve customer records.

You expose a function definition to the OpenAI API:


const tools = [
  {
    type: "function",
    name: "get_customer",
    description: "Retrieve a customer by ID",
    parameters: {
      type: "object",
      properties: {
        customer_id: {
          type: "string",
          description: "The unique customer ID"
        }
      },
      required: ["customer_id"],
      additionalProperties: false
    },
    strict: true
  }
];

This schema tells the model:

  • The tool is named get_customer.
  • It retrieves a customer by ID.
  • It accepts a string called customer_id.
  • The argument is required.
  • No additional arguments are allowed.

Defining the tool does not execute it. It makes the function available for the model to request.

The function definition also does not automatically grant database access. Your application must implement the function and configure the appropriate credentials and permissions.

3. Step 2 — The model returns a tool-call request

Your application sends the user's message and the tool definitions to the OpenAI Responses API.


const response = await client.responses.create({
    model: "YOUR_SUPPORTED_MODEL",
    input: "Find customer 123 in the database.",
    tools
});

The model may return a structured output item resembling this:


{
    "type": "function_call",
    "call_id": "call_abc123",
    "name": "get_customer",
    "arguments": "{\"customer_id\":\"123\"}"
}

Here is what each field means:

Field Purpose
type Identifies the output as a function call.
call_id Correlates the result with this specific request.
name Identifies the function your application must dispatch.
arguments JSON-encoded arguments for the function.

Notice that arguments is a JSON string in this representation. Your code parses it into a JavaScript object before using it.

The model does not normally return executable JavaScript for a standard function call. It returns a structured instruction to invoke a function.

The exact response structure depends on the API and tool type. See the official

OpenAI function-calling documentation

4. Step 3 — Your backend executes the requested function

The backend needs an implementation that maps the permitted tool name to actual code.


async function getCustomer({ customer_id }) {
    // Example: query your database using a parameterized query.
    const result = await db.query(
        "SELECT id, name, email FROM customers WHERE id = $1",
        [customer_id]
    );
    
    return result.rows[0] ?? null;
}

Then dispatch the tool call:


const args = JSON.parse(toolCall.arguments);

if (toolCall.name === "get_customer") {
  const customer = await getCustomer(args);
}

This is where the actual operation happens.

For example, the application may:

  1. Receive the model's request.
  2. Parse and validate the arguments.
  3. Authenticate the application user.
  4. Check whether that user may access the requested customer.
  5. Query PostgreSQL.
  6. 1. Convert the database result into a safe response.

Critical security detail: Do not let the model supply arbitrary SQL or choose an unrestricted function to execute. Use an allowlist of tool names, validate arguments on the server, and enforce authorization independently of the model.
