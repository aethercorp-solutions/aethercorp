Refactoring

Refactoring is the process of improving the internal structure of existing code without changing its external behavior. The goal is to make the code easier to read, maintain, test, and extend.

Think of it like renovating a house:

  • The rooms still serve the same purpose.
  • The plumbing, wiring, and layout are improved.
  • From the outside, it still works the same.

Example

Before refactoring:


def calc(a, b, c):
    if c == "add":
        return a + b
    elif c == "sub":
        return a - b

After refactoring:


def calculate(first_number, second_number, operation):
    if operation == "add":
        return first_number + second_number
    elif operation == "sub":
        return first_number - second_number

The functionality is identical, but the second version is easier to understand because of the clearer names.

Common refactoring techniques

  • Rename variables, functions, or classes to make their purpose clearer.
  • Extract a function to avoid repeating code.
  • Remove duplicate code by reusing existing logic.
  • Simplify complex conditions into readable expressions.
  • Break large functions into smaller, focused ones.
  • Reorganize files or classes for a cleaner project structure.

Why refactor?

Refactoring helps you:

  • Improve code readability.
  • Make debugging easier.
  • Reduce technical debt.
  • Make it safer and faster to add new features.
  • Improve testability.

When should you refactor?

Good times to refactor include:

  • Before adding a new feature.
  • After fixing a bug.
  • When you notice duplicated or confusing code.
  • During regular maintenance.

Refactoring vs. Rewriting

Refactoring Rewriting
Keeps the same behavior May change behavior
Improves existing code Creates new code from scratch
Lower risk Higher risk
Usually done in small steps Often done as a larger project

A useful principle is: refactor in small, tested steps. After each change, run your tests (or otherwise verify the behavior) to ensure the software still works the same.

Refactoring means improving the internal structure of code without changing its behavior. The goal is to make the code easier to read, maintain, test, and extend.

A practical way to refactor is to follow these steps:

  1. Make sure the code works first
    • Fix existing bugs before refactoring.
    • If possible, have tests in place.
  2. Find code smells

    Look for things like:

    • Long methods
    • Large classes
    • Duplicate code
    • Deeply nested if statements
    • Long parameter lists
    • Magic numbers and hardcoded strings
    • Repeated switch/case or if/else chains

Example 1: Remove Duplicate Code

Before


if (!self.selectedSalespersons)
    self.selectedSalespersons = [NSMutableArray new];

if (!self.selectedDivisions)
    self.selectedDivisions = [NSMutableArray new];

if (!self.selectedLabels)
    self.selectedLabels = [NSMutableArray new];

After

Create one helper:


- (NSMutableArray *)arrayOrCreate:(NSMutableArray *)array
{
    return array ?: [NSMutableArray array];
}

Then


self.selectedSalespersons = [self arrayOrCreate:self.selectedSalespersons];
self.selectedDivisions    = [self arrayOrCreate:self.selectedDivisions];
self.selectedLabels       = [self arrayOrCreate:self.selectedLabels];

Example 2: Extract a Method

Before


- (void)loadData
{
    // 50 lines loading models

    // 30 lines parsing

    // 40 lines filtering

    // 20 lines updating UI
}

After


- (void)loadData
{
    [self loadModels];
    [self parseModels];
    [self applyFilters];
    [self updateUI];
}

Each helper becomes much easier to understand.

Example 3: Replace Giant if-else

Before


if (context == Invoice) {

}
else if (context == SalesOrder) {

}
else if (context == Collection) {

}

After


switch (context) {
    case Invoice:
        [self setupInvoice];
        break;

    case SalesOrder:
        [self setupSalesOrder];
        break;

    case Collection:
        [self setupCollection];
        break;
}

Or even better, create separate classes if each context has significantly different behavior.

Example 4: Move Related Data into an Object

Instead of


@property NSArray *divisions;
@property NSArray *labels;
@property NSArray *models;
@property NSMutableArray *selectedDivisions;
@property NSMutableArray *selectedLabels;
@property NSMutableArray *selectedModels;

Create


@interface FilterState : NSObject

@property NSMutableArray *selectedDivisions;
@property NSMutableArray *selectedLabels;
@property NSMutableArray *selectedModels;

@property NSArray *divisions;
@property NSArray *labels;
@property NSArray *models;

@end

Then your controller simply has


@property FilterState *filterState;

instead of dozens of properties.

This is exactly the direction you were moving with your recent filter refactoring.

Example 6: Reduce Nested if Statements

Before


if (user) {
    if (user.name) {
        if (user.name.length > 0) {
            ...
        }
    }
}

After


if (!user || user.name.length == 0) {
    return;
}

// normal code

This is called a guard clause and makes the main logic much easier to follow.

Example 7: Replace Repeated Dictionary Access

Before


NSString *division = dict[@"division"];
NSString *label = dict[@"label"];
NSString *model = dict[@"model"];

After

Create a model:


@interface InvoiceFilter : NSObject

@property NSString *division;
@property NSString *label;
@property NSString *model;

@end

Instead of passing dictionaries around, pass an InvoiceFilter instance.

Refactoring Principles

A few principles consistently lead to cleaner code:

  • DRY (Don't Repeat Yourself): Avoid duplicating logic.
  • KISS (Keep It Simple, Stupid): Prefer simple solutions over clever ones.
  • SOLID: Design classes with clear responsibilities and loose coupling.
  • Single Responsibility Principle: Each class or method should have one reason to change.
  • Composition over inheritance: Reuse behavior by composing objects when appropriate.

Refactoring Workflow

When working on an existing codebase:

  1. Understand what the code does.
  2. Ensure it works (or add tests).
  3. Refactor one small piece at a time.
  4. Build and run after every small change.
  5. Commit frequently with focused changes.

For example:

  • Commit 1: Extract FilterState
  • Commit 2: Move parsing logic
  • Commit 3: Remove duplicated initialization
  • Commit 4: Simplify view controller
  • Commit 5: Rename methods and variables

This incremental approach makes it much easier to review changes and isolate regressions.
