Common architecture from the 2000s and early 2010s

That sentence describes a common architecture from the 2000s and early 2010s, where the web server and application server had clearly separated responsibilities.

1. Old approach: Web server + Application server

A typical architecture looked like this:


User's Browser
      │
      │ HTTP/HTTPS
      ▼
┌──────────────────┐
│    Web Server    │
│ Apache / IIS     │
│ Nginx            │
└────────┬─────────┘
         │
         │ forwards dynamic request
         ▼
┌──────────────────┐
│ Application      │
│ Server           │
│                  │
│ Java EE / .NET   │
│ WebLogic / JBoss │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│    Database      │
│ Oracle / MySQL   │
└──────────────────┘

The web server was primarily the HTTP-facing layer.

For example:


GET /customers/123

Apache or IIS would:

  • accept the TCP/HTTP connection
  • handle HTTP
  • serve static files such as HTML, CSS, JS, images
  • handle SSL/TLS in many deployments
  • perform URL routing/reverse proxying
  • forward dynamic requests to the application server

The application server was responsible for the actual application logic.

For example:


Customer customer =
    customerService.getCustomer(123);

if (customer.getBalance() > 100000) {
    customer.setPriority("VIP");
}

It could handle:

  • business rules
  • authentication/authorization
  • transactions
  • database access
  • sessions
  • messaging
  • complex workflows
  • enterprise integrations

So conceptually:

Web server = "Talk to the browser."

Application server = "Figure out what the request actually means."

2. Example: Old e-commerce application

Imagine an old Java enterprise shopping site.

A customer requests:


GET /checkout

The flow might be:


Browser
   │
   │ GET /checkout
   ▼
Apache HTTP Server
   │
   │ HTTP handling
   │ static content
   │ reverse proxy
   ▼
WebLogic / JBoss
   │
   ├── Check user session
   ├── Load shopping cart
   ├── Calculate discounts
   ├── Calculate tax
   ├── Check inventory
   ├── Create order
   └── Start database transaction
          │
          ▼
       Oracle DB

The application server might contain things like:


OrderService
CartService
PaymentService
InventoryService
CustomerService

The application server was often a large enterprise runtime providing infrastructure for those services.

3. Why did they separate them?

Because the web server and application server had different jobs.

Imagine 10,000 requests:


                ┌── Static image
                │
Browser ────────► Web Server
                │
                ├── CSS
                │
                ├── JavaScript
                │
                └── Dynamic request
                        │
                        ▼
                 Application Server
                        │
                        ▼
                     Database

The web server could efficiently handle things like:


/logo.png
/styles.css
/app.js
/index.html

while the application server handled:


POST /orders
POST /payments
GET /customers/123
POST /checkout

This separation also allowed organizations to scale them independently.

For example:


            Load Balancer
                │
     ┌──────────┴──────────┐
     ▼                     ▼
 Web Server 1          Web Server 2
     │                     │
     └──────────┬──────────┘
                ▼
      ┌─────────────────┐
      │ App Server Pool │
      │                 │
      │ App 1           │
      │ App 2           │
      │ App 3           │
      └────────┬────────┘
               ▼
            Database

This was particularly common in large enterprise systems.

4. Modern approach

Today, the distinction is much less rigid.

A modern application might look like:


Browser / Mobile App
        │
        │ HTTPS
        ▼
   CDN / Load Balancer
        │
        ▼
┌─────────────────────┐
│ Web / API Application│
│                     │
│ Node.js / Python    │
│ Java / .NET / Go    │
└──────────┬──────────┘
           │
     ┌─────┼───────────┐
     ▼     ▼           ▼
 Database  Redis     Other APIs

For example, with Next.js:


Browser
   │
   ▼
Next.js
   │
   ├── Render UI
   ├── API routes
   ├── Authentication
   ├── Business logic
   └── Database queries
          │
          ▼
       MongoDB

You don't necessarily have:


Apache → WebLogic → Database

Instead, the application itself can handle HTTP and business logic.

5. Your Node.js example

Suppose you have:


React
  │
  │ HTTPS
  ▼
Node.js / Express
  │
  ├── Authentication
  ├── JWT validation
  ├── Business logic
  ├── API endpoints
  └── MongoDB access

Your Node.js application might have:


app.post("/orders", async (req, res) => {

    // Authentication
    const user = verifyJWT(req);

    // Business logic
    const cart = await getCart(user.id);
    const total = calculateTotal(cart);

    // Database
    const order = await Order.create({
        userId: user.id,
        total
    });

    res.json(order);
});

Here Node.js is simultaneously doing the HTTP-facing work and application/business processing.

That's one of the biggest differences.

The key idea

The old statement:

"The web server handles HTTP; the application server handles heavy business processing."

is describing a time when those responsibilities were commonly separated into different server products and processes.

Modern development tends to say:

"Separate responsibilities into layers/services, but they don't necessarily need to run on separate server products."

That's why your modern React → Node.js → MongoDB/AWS applications can perform both the HTTP/API work and business processing inside the application layer, while infrastructure such as CloudFront, API Gateway, Nginx, or a load balancer handles the edge/network concerns.

Exactly — the important point is that the web server usually does not “figure it out” dynamically by itself. The routing behavior is normally configured by developers/DevOps.

Simple architecture


Browser
   │
   │ HTTP Request
   ▼
┌─────────────────┐
│   Web Server    │
│ Nginx / Apache  │
└────────┬────────┘
         │
         ├── Static request ──────► File
         │                         HTML/CSS/JS/Image
         │
         └── Dynamic request ────► Application Server
                                   │
                                   ├── Business logic
                                   ├── Database
                                   └── External services

How does it know?

The web server has routing rules.

For example, suppose you have:


GET /images/logo.png
GET /css/style.css
GET /products
POST /api/orders

Nginx might be configured approximately like this:


location /images/ {
    root /var/www;
}

location /css/ {
    root /var/www;
}

location /api/ {
    proxy_pass http://application-server:3000;
}

location /products {
    proxy_pass http://application-server:3000;
}

So:


/images/logo.png
       ↓
Nginx
       ↓
/var/www/images/logo.png
       ↓
Return file

But:


POST /api/orders
       ↓
Nginx
       ↓
Application Server :3000
       ↓
Order business logic
       ↓
Database

What happens technically?

When the request arrives:


GET /products/123 HTTP/1.1
Host: example.com

the web server examines things such as:

  • HTTP method: GET, POST, PUT, etc.
  • URL/path: /products/123
  • Host/domain: example.com
  • Headers
  • Sometimes query parameters

Then it matches those against its configuration.

For example:


Request
   │
   ▼
Nginx
   │
   ├── /static/*  → serve file
   │
   ├── /images/*  → serve file
   │
   ├── /api/*     → application server
   │
   └── /*         → application server

Old approach

In older web applications, you might have:


Browser
   ↓
Apache
   ↓
PHP / Java / ASP.NET application
   ↓
Database

Apache could determine:

"This is a PHP request, so I need to invoke PHP."

For example:


/index.php
      ↓
Apache
      ↓
PHP interpreter
      ↓
PHP code
      ↓
Database

Or with Java:


Browser
   ↓
Apache
   ↓
Tomcat
   ↓
Java application
   ↓
Database

Modern approach

Today, the web server/reverse proxy is often primarily a traffic router.

For example:


                ┌── React/Next.js
                │
Internet → Nginx ───┼── Node.js API
                │
                ├── Python API
                │
                └── Microservice

A request such as:


https://example.com/

might go to the frontend.


https://example.com/api/users

might go to Node.js.


https://example.com/api/ai

might go to a Python AI service.

The web server isn't deciding based on whether the request is "easy" or "heavy." The routing configuration determines where it goes.

One important distinction

There are actually two different concepts that are often confused:

1. Web server deciding where to route


Nginx
   ↓
"According to my configuration,
 /api/* goes to Node.js"

2. Application server deciding what business logic to execute


Node.js
   ↓
GET /api/orders/123
   ↓
OrderController
   ↓
OrderService
   ↓
MongoDB

So the web server generally decides which server/process receives the request, while the application server decides what the request actually means and what business processing should happen.
