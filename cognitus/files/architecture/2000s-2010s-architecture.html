2000s/2010s architecture

Yes. In that 2000s/2010s architecture, “services” usually meant backend components that the web/application server called to perform specific functions.

A typical system looked like: 


Browser
   │
   │ HTTP
   ▼
Web Server / Application Server
   │
   ├── Business Logic
   │
   ├── Authentication Service
   ├── Email Service
   ├── Payment Service
   ├── File Storage Service
   ├── Search Service
   └── Reporting Service
   │
   ▼
Database

Examples of services

Service What it did Typical technology
Authentication Service Login, sessions, passwords, permissions LDAP, Active Directory, custom DB
Email Service Send registration, password-reset, notification emails SMTP, Exchange
Payment Service Credit-card/payment processing PayPal, Authorize.Net, bank APIs
File Service Upload/download documents and images File server, FTP, NAS
Search Service Search products, customers, documents SQL queries, Lucene/Solr
Reporting Service Generate PDF/Excel/business reports Crystal Reports, SSRS, JasperReports
Logging Service Centralize application logs Syslog, Log4j, Splunk
Messaging Service Asynchronous communication between applications RabbitMQ, ActiveMQ, IBM MQ
Caching Service Store frequently accessed data Memcached, Redis
External API Service Communicate with third-party systems REST/SOAP

The Order Service, for example, might:

  1. Receive an order.
  2. Validate the customer.
  3. Check inventory.
  4. Calculate the price.
  5. Call a payment provider.
  6. Save the order to SQL Server.
  7. Call the email service.
  8. Return the result to the web application.

SOAP was particularly important

In enterprise systems of the 2000s and early 2010s, “service” very often meant a SOAP Web Service.

For example:


Web Application
      │
      │ SOAP/XML
      ▼
CustomerService
      │
      ▼
SQL Server

The request might look conceptually like:


<GetCustomer>
    <CustomerId>12345</CustomerId>
</GetCustomer>

and the service would return XML:


<Customer>
    <Id>12345</Id>
    <Name>John Smith</Name>
    <Email>john@example.com</Email>
</Customer>

Technologies such as .NET ASMX/WCF, Java JAX-WS, Apache Axis, and enterprise ESBs were common.

The important distinction from today's architecture

When we say:

2000s/2010s


Browser
   ↓
Web/App Server
   ↓
Services
   ↓
Database

the services might actually be separate enterprise applications, often communicating through SOAP, REST, or messaging.

Modern systems tend to make the boundaries much more explicit:


Browser / Mobile App
        │
        ▼
   API Gateway / CDN
        │
        ├── Auth Service
        ├── User Service
        ├── Order Service
        ├── Payment Service
        ├── Notification Service
        └── Search Service
                │
                ▼
       Databases / Caches / Queues

So the big evolution isn't that services didn't exist before. They absolutely did. The major change is that modern cloud development makes APIs, independently deployable services, containers/serverless functions, queues, managed databases, observability, and distributed systems much more central to the architecture.

And a lot of what you might recognize from your current Node.js/Lambda/MongoDB/AWS work is essentially a much more cloud-native evolution of those older concepts.

The simplest distinction is:

Web server = delivers HTTP content.

Application server = runs application/business logic.

1. Web server

A web server primarily handles HTTP requests and responses.

Examples:

  • Apache HTTP Server
  • Nginx
  • Microsoft IIS

For example:


Browser
   │
   │ GET /logo.png
   ▼
Nginx
   │
   └── returns logo.png

It is very good at:

  • Serving HTML, CSS, JavaScript
  • Serving images/files
  • Handling HTTP/HTTPS
  • SSL/TLS termination
  • Reverse proxying
  • Load balancing
  • Caching
  • Routing requests

For a static website, you might only need a web server:


Browser → Nginx → HTML/CSS/JS

2. Application server

An application server executes your application's code and handles business rules.

For example:


Browser
   │
   │ POST /orders
   ▼
Web Server
   │
   ▼
Application Server
   │
   ├── Validate customer
   ├── Calculate price
   ├── Check inventory
   ├── Create order
   └── Save to database
   │
   ▼
Database

Examples historically included:

  • Tomcat / JBoss / WebLogic for Java
  • ASP.NET / IIS for Microsoft environments
  • WebSphere for enterprise Java
  • Node.js applications
  • PHP application runtimes

Why were they separated?

In the 2000s, a common enterprise architecture was:


                    ┌──────────────┐
Browser ────────►   │ Web Server   │
                    │ Apache/IIS   │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ Application  │
                    │ Server       │
                    │ Java/.NET    │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │  Database    │
                    │ Oracle/SQL   │
                    └──────────────┘

The web server could handle the HTTP-facing work, while the application server handled the heavy business processing.

A modern example

Today, the distinction can become blurry.

For example, with Node.js:


Browser
   ↓
Nginx
   ↓
Node.js / Express
   ↓
MongoDB

Nginx is the web server/reverse proxy, while Express/Node.js is effectively the application server.

With AWS:


Browser
   ↓
CloudFront
   ↓
API Gateway
   ↓
Lambda
   ↓
MongoDB

You don't necessarily have a traditional "application server" running 24/7. Lambda executes the application logic on demand.

Easy way to remember

Think of a restaurant:

Web server = waiter

"Here's the menu. I'll receive your request and deliver the response."

Application server = kitchen

"I'll actually process your order, apply the rules, prepare the result, and interact with the ingredients/database."

Database = storage room

"Here's the information you need."

So when you see:

Browser → Web/App Server → Database + Services

the Web/App Server is often where the application's backend code actually runs, while the services are additional systems it calls for specialized functionality.
